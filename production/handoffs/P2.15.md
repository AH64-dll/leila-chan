# Handoff — P2.15: Stage FX shaders: shake_big, flicker (photosensitive → dim), darken, vignette_red, glitch, text_bleed, desaturation by stage

## Round 1  (2026-11-04, agent: commandcode)

### Summary
The stage-3/4 effect vocabulary now exists end to end. `FX.gd` gained the stage baseline: `casting.stage_fx`
(generated by `build_casting.py`) maps every stage to its desaturation amount, `set_stage()` resolves the row
and pushes it to the host, and `Director` re-syncs it on every `GameState.stage_changed` (and at boot), so a
date that opens mid-campaign starts already drained. The Character host implements `shake_big` (0.6 s heavy
camera shake, cut under reduced motion), `flicker` (stepped strobe, or a single slow **dim** in photosensitive
mode — never faster than 3 Hz), `darken` (to 40%), `vignette_red`, `glitch` (scanline displacement + RGB split
on the whole screen) and `text_bleed` (the text box's bottom edge runs down over the UI). All six are gated and
cooled by the existing `casting.fx` budgets and are force-fireable from the F6 menu.

One finding shaped the architecture: a Godot 4 2D screen texture is a **single copy per frame**, so stacked
full-screen sampling shaders cannot compose — a `flicker` frame at level 1.0 erased the stage-3 desaturation
(measured: world chroma jumped from 2.84 to 12.31). The six rects were collapsed into **one** `stage_fx.gdshader`
pass (`Character/OverlayFX/StageFX`) whose uniforms are the whole vocabulary; the P1.11 twitch split moved into
the same pass (a second sampling rect would have the same erasing effect). Measured after the fix: the lit
flicker frame equals the baseline exactly (chroma 2.84 / lum 20.33 vs 2.84 / 20.29), and one pass holds 251 fps
on llvmpipe and 3354 fps on the Radeon 760M with all six effects live plus the stage-5 drain.

### Deviations from the design bible
No behaviour deviates from docs/02 §2.3 / §5, docs/01 §3 or docs/03 §4. Three interpretations are worth a
reviewer's eye (none needs a DCR):
1. **Where the fx table lives.** docs/07 §2's tree sketch mentions `data/fx.json`; the implemented table is
   `casting.json["fx"]` (P1.11's decision, documented in docs/10 §2.2), and the stage baseline is the new
   `casting.json["stage_fx"]` from the same generator. No second fx file was introduced.
2. **The stage baseline's shape.** docs/01 §3 gives the onset ("backgrounds desaturate" at stage 3) and
   docs/03 §4 gives the rate (`saturation × (1 − 0.15·stage)`), so `stage_fx` is 0 at stages 0–2 and
   0.45 / 0.60 / 0.75 at 3 / 4 / 5 — the doc's formula applied from the doc's onset, in data, asserted
   in `tests/test_data_files.py`.
3. **The pass sits above the UI.** `text_bleed` needs the dialogue box in its sample and docs/02 §2.3 calls
   glitch "on the whole screen", so the one screen pass covers world + UI; the stage FX therefore also dim and
   drain the dialogue box (readable at 0.40 darken, see `01_darken_40_percent.png`). BlushGlow and DateFX stay
   below the UI as before. If META later wants UI immunity, it needs a render target, not a second
   screen-sampling rect (see the shader header).

### Deviations from the design bible
Round 1 claimed "None". That was wrong: one doc conflict exists and is now filed.

**DCR — docs/05 §0.4 vs docs/02 §2.3 / docs/10 §2.2 (photosensitive `flicker`)**
- **Docs disagree.** `docs/05_META_EVENTS.md:12-13` (hard rule §0.4): "Photosensitive mode **disables**
  flicker/invert." `docs/02_DIRECTOR_PROTOCOL.md:126`: `flicker` … "(photosensitive-safe mode: dim instead)".
  `docs/10_CASTING.md:159-161`: "`flicker` becomes a single dim". The safety playbook repeats "flicker dims,
  `invert_flash` off".
- **What ships** (unchanged from round 1, now on purpose): the cue becomes **one dim** — 1/3 s ramp to 0.55,
  0.5 s hold, 1/3 s ramp back = 1.167 s, one luminance pair (2 edges), ≤ 2 Hz against the 3 Hz limit;
  `invert_flash` is dropped as `photosensitive` (`FX.PHOTOSENSITIVE_OFF`).
- **Judgement.** The strictly *safer* of the two readings is docs/05's — no luminance change at all. The dim
  is the reading two other docs and the safety playbook mandate, it is WCAG 2.3.1-compliant at 1 pair per
  1.167 s, and it keeps the beat the director protocol asks the model to use. So the conflict is the docs',
  not the code's — but docs/05 §0 is a **non-negotiable hard rule**, so it cannot be amended by this task.
- **Proposed text (needs the user, protocol §6):** docs/05 §0.4, second sentence →
  "Photosensitive mode replaces `flicker` with a single slow dim and disables `invert_flash`."
- **If the producer prefers the strict rule instead:** change docs/02 §2.3 + docs/10 §2.2 to "skipped",
  add `"flicker"` to `FX.PHOTOSENSITIVE_OFF`, and the host's dim pattern (`FX_FLICKER_DIM_STEPS`) plus
  `FXStageHostTest::test_photosensitive_flicker_is_a_dim_not_a_strobe`'s dim half go away. One-line change
  either way; no third behaviour is needed.
- **Impact:** no code changes until the decision lands. Until then the implementation matches docs/02 §2.3,
  docs/10 §2.2 and the safety playbook.
