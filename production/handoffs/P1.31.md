# Handoff — P1.31: Gate-r1 remediation: safety-rejected player input must not deadlock the chat UI

## Round 1  (2026-11-04, agent: commandcode)

### Summary
A Safety-rejected player line is no longer a dead end. `Director.submit_player_input` now routes the
rejection through `_reject_unsafe_input()`: it writes the failed turn record (`meta.status = "failed"`,
`error.code = "unsafe_input"`) and answers with one in-character refusal beat through the ChatUI beat
path (`ChatUI.reject_turn` → `begin_beat` / `replace_beat` / `end_beat` / `end_turn`), which is the same
reveal-then-unlock path a normal reply takes. The input box therefore comes back and "Leila is typing…"
goes away instead of staying up forever, and the refused submission is present in the session
transcript. The refusal line is data (`game/data/fallbacks.json` → `unsafe_input_fallbacks`, stage 0–2 and
stage 3+ variants), read through `TurnValidator.get_input_refusal()`; it deliberately plays no cue so an
input rejection never spends the turn's docs/02 §5 cue budget.

### Deviations from the design bible
**DCR (design change request): document the input-side safety refusal in docs/02.**
- *What to change:* docs/02 §4 step 0 should name the input check and its terminal handling, e.g.
  "0.1 Safety check — a line the filter refuses never opens a turn: she answers with one in-character
  refusal beat, the turn is recorded as failed (`unsafe_input`) and the input is released." Add the
  matching row to §7 ("Rejected player input | input scan at step 0.1 | refusal beat + failed transcript
  record; no turn starts").
- *Why:* §7/§8 only define what happens to unsafe *output* ("Redact"); §4 step 0 lists hooks but no
  rejection outcome, so the fixed behaviour had no documented shape to implement against — F3 had to
  decide the UX ("a pout line or a system message"). The chosen UX is the refusal line; without a doc row
  the next reader cannot tell whether the refusal is design or improvisation.
- *Impact:* docs only; no code or data change. Refusal copy already lives in data
  (`game/data/fallbacks.json` → `unsafe_input_fallbacks`) for NAR to edit.

No implementation deviation from docs/02 §4/§8: the refusal text goes through the same single scan
(`SaySafetyGate.filter_text`), the same beat path and the same transcript record shape as every other
turn close.

### Open questions / follow-ups
- **No production caller yet (F1).** `Date.gd` still has no controller: nothing in the shipped scene calls
  `Director.submit_player_input`. The F1 controller task must connect `ChatUI.player_turn_sent` →
  `Director.submit_player_input` (as the regression test does) and must not add a second `turn_failed`
  consumer that aborts the UI — the refusal beat already releases it.
- **`Date._current_turn` counts submissions, not completed turns** (`game/scenes/Date.gd:307`). A rejected
  line still increments it; the F1 controller should move that counter onto `turn_completed` (or to
  `GameState.turn`) so scenario `max_turns` is not spent on refusals. Out of scope here.
- **Refusal copy is two lines deep** (stage 0–2 / stage 3+). NAR may want a fuller pool (and a stage 4–5
  voice) in `game/data/fallbacks.json`; the Director needs no change for that.
- **Cue stays `"none"`** on this path by design: the refusal is an input-path event, not a streamed reply,
  so AudioDirector's budget is never touched. If AUD wants a sound, the Director must gain a deliberate
  `play_cue` call here.
- **Transcript key reuse:** a rejection does not advance `GameState.turn`, so a session can log `turn: 0`
  twice (first `failed`/`unsafe_input`, then `completed`). If tuning tooling needs unique keys, add a
  rejection sequence number rather than advancing the game clock for a turn that never happened.
- **`turn_failed` still has no production consumer.** The UI no longer depends on it; leaving it as an
  observable is deliberate (DebugOverlay/telemetry can pick it up in a later task).
- **Direct-drive note:** `ChatUI.reject_turn()` assumes the submit locked the UI
  (`ChatUI.begin_turn_wait()`), which is the production flow the test drives. A dev tool calling
  `Director.submit_player_input()` directly still sees the refusal and never a locked box, but
  `turn_displayed` does not fire (no turn was ever open) — the F1 controller should keep submissions on
  the InputBox path.
