# Handoff — P2.25: merge hygiene — merges must not clobber branch work

## Round 1  (2026-11-04, agent: commandcode)

### Summary

There is now a merge gate. `tools/merge_check.py` diffs every file changed on **both** sides since the merge-base
and answers two questions: before a merge, which lines each side's copy lacks (and what a `--theirs`/`--ours`
resolution would delete); after a merge, did the merge commit keep every line each parent gained since that base.
A file that comes out of the merge as the *other* parent's copy verbatim is reported as `STALE-COPY` and fails —
that is exactly what `50752b7` did to `game/tests/DateSceneTest.gd` (15 lines, including P1.16's
`test_photosensitive_wiring` and `test_ambience_forwarding`), and running the tool on that real commit fails it.
The check is wired into the producer's integrate step (`.claude/skills/leila-producer/SKILL.md` §4) and the work
protocol (§3), documented in `production/MERGE_CHECK.md`, and covered by 14 pytest cases that rebuild the P1.16
shape in a synthetic repository. No game code changed.

### Open questions / follow-ups

- **Known limit, documented in `production/MERGE_CHECK.md` §Limits:** the audit is line-based, so a semantic
  revert that keeps every line, and a merge that resurrects a line the other side deleted, are not detected.
  Neither is a P1.16-class stale replacement, and an AST-level diff is not warranted by E22; if a later gate wants
  it, propose it as its own ticket rather than widening this check.
- **CI cannot run it:** `actions/checkout` is shallow, and both the pre- and post-audit need the merge base and
  both parents. This is intentionally a producer/local gate; if CI ever gates PR merges, fetch both parents and
  run `--post`.
- **E34a remains the producer's action:** the restoration of the four approved handoffs is separate from this
  ticket. The tool independently finds the same loss (`50752b7` → `DELETED-BY-MERGE production/handoffs/P1.14.md`),
  so the gate will now fail any repetition of that mistake.

### Open questions / follow-ups

- **Rename detection is git's default 50% similarity.** A move that rewrites more than half the file is still a
  delete+add and is therefore classified as `DELETE-VS-EDIT`/`BOTH-DELETED` by content, which is the same answer
  git's merge gives (it will not pair the move either). `MERGE_CHECK.md` states the limit.
- **`RENAME/EDIT` passes when the merged copy holds every added line.** That is a deliberate, tested verdict: git
  follows the rename, so calling it a failure would contradict the merge in front of the producer. If the project
  ever wants a human look at every move, the status is already dedicated and can be moved to `REVIEW_STATUSES`
  without touching the classification.
- The round-1/2 limits stand and are unchanged in `MERGE_CHECK.md`: line-based detection, additions only, needs both
  parents (so not a CI gate), post-check runs after the commit unless `--staged` is used.
- `production/MERGE_CHECK.md` and this handoff name `458f051` as this branch's latest `main` merge. If `main` moves
  again before integrating, re-run `--post` on the new merge and cite that id; the documented rule is "run it before
  the next commit lands".
