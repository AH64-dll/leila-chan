## Round 1  (2026-11-02, agent: swe2)

### Summary
`game/llm/IncrementalJson.gd` is a transport-independent incremental JSON parser (RefCounted): a backend feeds
raw text chunks via `feed(chunk) -> Array[Dictionary]` and gets back the events that chunk completed, in stream
(schema) order — `field`, `beat_start`, `beat_field`, `say_chunk`, plus a terminal `error` event the doc leaves
implicit. `finish()` reports `Status` (OK / TRUNCATED / ERROR); `get_value()` mirrors a full `JSON.parse` of the
completed portion. The test corpus is 75 real Turn outputs re-serialised from the experiment recordings
(`experiments/results_v3.json` + `experiments/windows/tool_test_v3.json`) plus 4 synthetic fixtures for the
escape/unicode cases the recordings lack; 15 gdUnit4 cases prove event order equals a full parse under
whole-feed, per-character, fixed-size and seeded-random splits, and that truncation emits only a valid prefix.

### Deviations from the design bible
None for requirements. Conventions fixed where docs/07 §3.2 is open (documented in the class docstring
`game/llm/IncrementalJson.gd:14`):

- `mood` (a leaf object) emits one `field("mood", Dictionary)` when it closes — the doc only defines `field` for
  "a scalar field"; a single close event is the least surprising reading and is what Director step 7 consumes.
- `beats` emits no `field` event — its content arrives through `beat_*` events only.
- `say` emits `say_chunk` partials AND a closing `beat_field(i, "say", full_text)` like other beat scalars —
  consumers need an explicit "line complete" signal for the typewriter.
- An extra `{"type": "error", "message", "offset"}` event exists beyond the four documented names — needed so
  P1.09's broken-JSON fallback can fire without polling `has_error()`.
- Godot's `JSON.parse` returns float for every number; the parser emits int for integral literals (schema says
  intensity/mood are integers) — asserted equal via normalisation in tests, and `get_value()` keeps ints.
- The experiments recorded parsed `out` objects, not raw token streams (non-streaming API); fixtures are the
  recorded outputs re-serialised verbatim to the compact JSON a stream carries. Flagged for honesty: they are
  recorded model replies, but not literally captured bytes.

#### DCR-1 — event contract in docs/07 §3.2 and the closing-`say` note in docs/02 §4

**Docs/sections:** `docs/07_TECH_ARCHITECTURE.md` §3.2; `docs/02_DIRECTOR_PROTOCOL.md` §4 step 5 (and the
broken-JSON row of §7).

**Why:** §3.2 names four events but not their payloads or the cases the parser must decide; P1.08, P1.09,
P1.13 and P1.19 are about to encode those decisions. §4 step 5 does not yet say that the closing
`beat_field("say", full text)` must not be replayed to the typewriter, which would duplicate every line.
Round 1 fixed these conventions in code and the design review (DES-3) asked for the formal filing.

**Proposed docs/07 §3.2 text** (replace the section body):

```markdown
### 3.2 IncrementalJson
A tiny state machine over the token stream. It is transport-independent: a backend feeds decoded text
chunks to `feed()` and receives the events that chunk completed, in document (schema) order.

| Event | Payload | When |
|---|---|---|
| `field` | `name: String, value: Variant` | A root-level field's value closed. `mood` is the only object-valued field: one `field("mood", {affection, trust, stress})` when it closes. `beats` emits no `field` event; its content arrives through `beat_*`. |
| `beat_start` | `index: int` | `beats[index]` opened. |
| `beat_field` | `index: int, name: String, value: Variant` | A beat scalar closed. For `say` this is the line-complete signal and carries the full text. |
| `say_chunk` | `index: int, text: String` | Partial decoded `say` text. Chunk boundaries are arbitrary; an empty `say` emits no chunk. |
| `error` | `message: String, offset: int` | Terminal syntax error. Any decoded `say` text is flushed as `say_chunk` first, so `error` is always the last event. |

`finish()` returns `OK` (root closed), `TRUNCATED` (stream ended mid-structure) or `ERROR`.
`get_value()` returns the assembled value of the completed portion: the full value once the root closed,
otherwise the outermost container built so far (fields whose values closed; a still-open nested container
is not attached), or `null` if no root container opened. Partial `say` text is available only through
`say_chunk`. Pending unterminated tokens (a number without a delimiter) commit nothing. Numbers decode to
`int` when integral and `float` otherwise (Godot's `JSON.parse` gives floats for both).

Because the schema fixes property order (`read, inner, music, fx, beats[feeling, intensity, cue, say], mood, memory, action`),
the parser knows what comes next — no lookahead needed.
```

**Proposed docs/02 §4 step 5 text** (add the note under the stream stage):

```markdown
 │      on beat.say chunk → Safety.scan → Corruption.filter(stage) → Typewriter.push()
 │      (the closing beat_field("say", full) only marks the line complete — never
 │       push that full text to the typewriter again; the chunks already did)
```

**Proposed docs/02 §7 note** (broken-JSON row): `IncrementalJson` flushes the decoded `say` prefix before
the terminal `error`, so "show the partial `say` text" can consume the already-emitted `say_chunk` events.

**Impact:** no code or content change; the docs catch up with shipped behaviour. No pillar, safety rule or
OPEN decision is touched. Consumers must follow the table above (P1.08 routes fields/beat fields, P1.09
shows partial say on error, P1.13 typewrites chunks only, P1.19 scans chunks and avoids double-scanning the
closing field). Producer accepts and schedules the doc update, or amends the text.
