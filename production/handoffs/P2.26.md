# Handoff — P2.26: first-beat latency — measured, attributed, and priced

## Round 1  (2026-11-04, agent: commandcode)

> Round-2 note: the numbers in this section were re-measured with the corrected `visible_ms` model (the
> safety filter holds **compact** characters, not raw ones) and on a CUDA build started for round 2. They
> are the numbers of record; `## Round 2` lists what changed and answers every review finding by ID.

### Summary

The 7.5 s first beat is **not** model time-to-first-token. It is the ~48 JSON tokens the model must emit
*before* the first `say` character, paid at the 4B model's decode rate. Replaying the exact prompts 39 real
production turns sent (`production/playtests/P1/transcripts`), the shipped path medians are **5.08 s** to the
first usable `say` and **6.04 s** to the first character the screen may show on the CPU host, versus
**1.00 s / 1.16 s** on a real CUDA host (RTX 4050, CUDA 13.4 build, `-ngl 99`). The breakdown closes: 68.3 %
pre-say decode, 15.7 % prompt prefill, 15.9 % the safety filter's 34-compact-character holdback, 0.2 % HTTP.
Moving `read`/`inner` behind `beats` — prototyped and measured, **not shipped** — takes CUDA to 0.72 s / 0.91 s
and the CPU host to 3.69 s / 4.57 s, i.e. **the prescribed AC clears at the median on the target hardware**
while every docs/02 §1 timing property (music/fx and the beat's feeling/cue before its text) still holds.
Because that reorder changes docs/02 §3 and a pinned test, it goes out as **DCR-1**, with the numbers below.
No game code changed this round. The CPU-host path cannot reach 1.0 s at all (its floor is the safety
holdback plus six tokens), so D13's deviation is restated as hardware-qualified.

## 1. Where the time goes (measured, not modelled)

### 1.1 The chain these numbers measure

```
POST ─► headers/queue ─► prefill (prompt tokens) ─► first token ─► pre-say decode
     ─► first `say` character ─► safety holdback (34 compact chars) ─► first character on screen
```

Each landmark is one clock (`tools/llm/latency_breakdown.py`), and the last two are the game's own:
`Safety._holdback = max(16, _max_phrase+1) = 34` chars (`game/autoload/Safety.gd:12,289`; the suite prints
"stream holdback: 34 chars"), held on the **separator-free compact views** (`SafetyText.compact`), so the
first character can appear after more *raw* characters than the holdback (the harness prints that optimistic
raw-char landmark as `R` beside `visible`). After the cut, `_drain` also trims to a token boundary and holds
trailing patterns; `TextBox.say_chunk` hands the released text to the 40 cps typewriter, so the *first*
character appears on the next frame (`game/scenes/ui/TextBox.gd:52-57,76-84`, `game/scenes/ui/Typewriter.gd:19`).

Inputs: `session 1`'s six consecutive recorded prompts and their recorded JSON schema, re-sent verbatim
(`messages` + `response_format` + that turn's `sampling` row + `max_tokens 600`), to
`Qwen3.5-4B-Q4_K_M.gguf`, `-c 8192 -np 1`, `cache_prompt=true`. The schema order is restored to docs/02 §3 —
the transcript's copy is alphabetical because `TranscriptLogger.gd:300` calls `JSON.stringify` with its default
`sort_keys=true` (S3 finding, §8.6).

### 1.2 Shipped order, warm prefix — CPU host vs CUDA (medians of 6 turns)

| term | CPU host (6 threads, 11.2 tok/s) | CUDA (RTX 4050, 53.3 tok/s) |
|---|---|---|
| HTTP + queue (first byte) | 13 ms (0.2 %) | 14 ms (1.2 %) |
| prefill of 69–83 new tokens | 947 ms (15.7 %) | 116 ms (10.0 %) |
| pre-say decode, 48 tokens | 4124 ms (68.3 %) | 878 ms (75.8 %) |
| **first usable `say`** | **5076 ms** | **1000 ms** |
| screen-visible safety holdback (34 compact chars) | 961 ms (15.9 %) | 158 ms (13.6 %) |
| **first character on screen** | **6036.5 ms** | **1157.5 ms** |
| whole turn (all beats + tail fields) | 11691 ms | 2296 ms |
| the same on-screen landmark counted on raw chars (`R`) | 5806.5 ms | 1133.0 ms |

Per-token cost: 89.3 ms (CPU) vs 18.7 ms (CUDA) — the decode rate is the entire hardware difference
(11.2 vs 53.3 tok/s), not the prompt. The holdback term is larger than round 1 reported because it is now
counted on the filter's compact view (`R` is the old, optimistic raw-char count).

### 1.3 First beat of a session (cold KV, `cache_prompt=false`; the whole 986-token prompt)

| | CPU host | CUDA |
|---|---|---|
| prefill of 986 tokens | 8521 ms (116 tok/s) | 427 ms (2014 tok/s) |
| first usable `say` | 12532 ms | 1296 ms |
| first character on screen | **13503 ms** | **1489 ms** |

So the *first* beat after a server launch is 2.2× the steady-state cost on the CPU host and 1.3× on CUDA: the

### 1.4 What the 39 recorded production turns say (`production/playtests/P1`, CPU host)

| metric | median | p95 | max |
|---|---|---|---|
| first byte | 21 ms | 274 ms | 358 ms |
| first token (prefill + ttft) | 945 ms | 5024 ms | 12437 ms |
| first usable `say` | **5359 ms** | 9679 ms | 17218 ms |
| … of which pre-say decode (`first_say − first_token`) | 4362 ms | 7114 ms | 8320 ms |
| whole turn | 12044 ms | 21054 ms | 23484 ms |
| prompt tokens re-evaluated (the part the KV cache missed) | 68 | 567 | 1449 |

My replay of the same six turns reproduces them like-for-like: first `say` median **5076 ms** versus the
**5197 ms** those six recorded turns measured (per-turn deltas −443…+91 ms), so the harness is faithful; the
replay is load-sensitive at the ±10 % level, which is why the committed artifacts are the evidence of record.

**The pre-say token census** (server `/tokenize`, **all 39** recorded outputs — every one has a usable
`"say"` landmark): **49 tokens** median, min 42, p95 77, max 81, spent on
`{"read":"…",` 6 · `"inner":"…",` 13 · `"music":"…"` 6 · `"fx":"…"` 5 · `"beats":[{"feeling":"…","intensity":N,"cue":"…","say":"`
22 (piece-wise sums exceed 49 because the segments' boundary tokens are shared). The timing agrees:
4362 ms ÷ 89.3 ms/token = 48.8 tokens.

**The prefill cliffs.** Prefill is 13.6 % of all turn time (70.6 s of 518.9 s) but lands unevenly: 6 of 39 turns
paid 3.9–12.2 s because the KV prefix was invalidated, and the cause is the *layout*, not the length:

- turns 5→6 and 8→9 (session 1): a new **memory fact** landed. `memories` sits before `rules` in the system
  message, so the first differing character is at char 1617 of the 3439-char **system message** (turn 6) and
  char 1682 of 3473 (turn 9); the content-concatenated prompts are 4467 and 4935 chars. The server reused
  **0** tokens (prompt_n 1298/1449, prefill **10856 / 12235 ms**).
- turns 11→12 and 12→13 (s1) and 12→13 (s2): the 12-exchange **history window slid**, so the divergence is at
  the start of the history, *after* the system message → reuse 944–971 tokens, prompt_n 434–567, prefill
  **3973–5011 ms**.

I probed the cache rule directly on the CUDA server (round 2, `max_tokens=1`, same prompt replayed with one
character changed):

| change | prompt_n | cache_n |
|---|---|---|
| replay unchanged | 4 | 1233 |
| one char changed at 1 600 of 3 374 in the system message | 1239 | **0** |
| one char changed at 2 800 of 3 374 (still in the system message) | 518 | 721 |
| extra clause appended to the last user message | 31 | **1211** |
| recorded turn 6 (the memory-fact turn) | 1298 | **0** |

So this server reuses a prefix only up to a point that is *before* the change, and the reuse granularity is
coarser than a token (0 while the change sits deep in the system message, 721/1 237 near its end). The
actionable direction is unambiguous and is what DCR-2 rests on: **a change appended at the tail leaves the
whole prefix cached**, while a change inside the system message above the history can cost all of it.

### 1.5 The order lever — measured prototypes (same prompts, same servers)

| schema order (top level) | pre-say tokens | CPU: first `say` / on screen | CUDA: first `say` / on screen |
|---|---|---|---|
| `read, inner, music, fx, beats, …` (shipped) | 47.5 | 5076 / 6036.5 ms | 1000 / 1157.5 ms |
| `music, fx, beats, read, inner, …` | 30.5 | 3690 / 4571 ms | 722 / **909 ms** |
| `beats, read, inner, music, fx, …` | 21 | 2842 / 3677.5 ms | 530 / 669 ms |
| `beats[{say, feeling, …}], …` (say first) | 6 | 1524 / 2408 ms | 272 / 464 ms |
| alphabetical control (`action` first) | 26 | 2519 / 3668 ms | 658 / 844 ms |

Per-token cost is unchanged (18.8–19.1 ms CUDA, 87.7–99.5 ms CPU); only the token count moved.

The DCR-1 order's **median** clears the 1.0 s AC on CUDA (909 ms) but its p95 does not (**1431 ms**): five of the
six turns land at 853–922 ms and turn 5 emitted *pretty-printed* JSON (59 pre-say tokens instead of 30–34, all
whitespace). That tail is why DCR-1 now also carries a `rules.md` "compact JSON" clause (DES-6).

The **control run** is what proves the lever is the *schema* order and not the prompt's ordering sentence: with
the transcript's sorted copy on the wire the model emitted `{"action":"none","beats":[{"cue":"giggle",…` even
though the system message says "Respond ONLY with JSON in this exact order: read, inner, music, fx, beats…".

### 1.6 Where `music`/`fx` land (why the row above matters)

`music`/`fx` close before the first `say` character in both recommended orders — measured on the RTX 4050 as
`music` value close − first `say` char over four turns: **−503 ms** shipped (27 tokens at 18.6 ms/token: the
`read` + `inner` values are 19 of them), **−466 ms** under DCR-1's order, and **+1278 ms** when `beats` goes
first (the whole beats array, with all of its `say` text, is decoded before `music`). That is why DCR-1 recommends `music, fx, beats, read, inner, …`, not `beats` first: the
face/sound-before-text property survives numerically (−466 ms is within 37 ms of the shipped −503 ms).

### 1.7 The terms that are *not* the problem

- **Model ttft.** First token is 122 ms (CUDA) / 952 ms (CPU) *including* prefill of the new tokens; there is no
  queue to speak of (one slot, one in-flight turn, first byte 12–15 ms).
- **Safety scan cost.** `tools/test.sh` measures the streaming filter at **≈555 µs per `say_chunk` call** over
  11271 calls (547.5–560.1 µs across runs); the first beat crosses the holdback in ~10 chunks, i.e. **< 6 ms** — 0.1 % of the first beat.
  The filter's *holdback* is the real safety term (158 ms CUDA / 961 ms CPU), and it is a correctness feature,
  not a bug to shave.
- **Typewriter.** 40 cps, clamped 35–45 (`Typewriter.gd:19,31-34`); the first character is not delayed by it (a
  60-char line still takes 1.5 s to finish appearing — visible pacing, outside this ticket).

## 2. Root cause and the honest verdict

**Root cause:** the `say` text is the 5th field of the object and the 4th field of the first beat, so the model
must decode ~48 tokens of `read`, `inner`, `music`, `fx` and the beat head before the first displayable
character exists. At 11.2 tok/s (CPU host) that is 4.1 s; at 53.3 tok/s (RTX 4050) 0.88 s. Adding the prompt and
the holdback gives 6.04 s / 1.16 s.

**Against the AC** ("first beat on screen < 1.0 s median on the RTX 4050"): the shipped order measures
**1.1575 s** — a 16 % miss, not a 7.5× one. With DCR-1 (`music, fx, beats, …`) it is **0.909 s** at the median
(p95 1.431 s, carried by one pretty-printed turn — see DES-6) and with `beats` first **0.669 s**. On the CPU
host no design meets it: the measured floor with `say` first is **2.408 s**, and 0.887 s of that is the safety
holdback alone. The holdback and the pre-say prefix are why the CPU host cannot be the release target.

**D13's headline number is a different prompt.** `bench_p121.py` sends a hand-written system prompt, not
`PromptBuilder`'s output, and its pre-say prefix ran ~81 tokens; the shipped prompt's median is **5.36 s**
(39 recorded turns). The "1.86 s CUDA" in the journals fits the same arithmetic: 1.16 s warm plus its
~33 extra pre-say tokens at 18.7 ms ≈ 1.78 s, plus a colder prefix.

## 3. What is cheap, and what needs a decision

| Lever | Effect (measured) | Cost | Verdict |
|---|---|---|---|
| Schema order: `music, fx, beats, read, inner, …` | CUDA 1157.5 → **909 ms** (−21 %); CPU 6036.5 → 4571 ms | ~12 lines + docs/02 §1/§3/§4 + 1 pinned test + prompt-lab order | **DCR-1**, recommended. Clears the AC median on CUDA and keeps every docs/02 §1 timing property. |
| Compact JSON in `rules.md` (no newlines/indentation) | the one pretty-printed turn cost 59 pre-say tokens vs 30–34 (+518 ms first `say`, 1431 vs 853–922 ms on screen) | one sentence in `rules.md`, folded into DCR-1 | **DCR-1 scope**, not yet measured as a fix. |
| Schema order: `beats` first | CUDA 669 ms | same, but music/fx trail the first line by ~1.28 s | Not recommended; kept as the measured upper bound. |
| Prompt-layout cache stability | median ~0; removes 4–12 s cliffs and most of the 8.5 s cold prefill | PromptBuilder layout + docs/08 §1 | **DCR-2** (§7). Cheap to implement, delivers what docs/07 §3.1 already promises. |
| Warm-up request at launch | first beat of a session only: CUDA 1489 → ~1158 ms, CPU 13503 → ~6037 ms | one 1-token POST when the server is ready | Follow-up (§8.2). No doc change, needs a prompt-layer seam. |
| Cap `inner` at 60 chars (now ≤ 90) | ~4–6 tokens off the long tail (−0.1 s CUDA) | data + docs/02 §1.1 | Not worth a round on its own; fold into DCR-1 if it happens. |
| CPU thread tuning (`-t 12`) | **worse**: 22–62 s vs 9.0 s per 120-token reply (2.4–6.9× slower, SMT/thermal) | — | Rejected, measured. |
| Speculative decoding / smaller model | would cut the decode term 1.5–2.5× | a local draft GGUF (cannot be committed) | Follow-up (§8.4). |

**No game code was changed.** The lever that clears the AC contradicts docs/02 §3's field table and the
*fixtures* of `game/tests/IncrementalJsonTest.gd:262-300` (the assertions are relative indices and stay valid;
see DES-7): "music/fx and the beat's feeling/cue land before that beat's text" is a design property (the face
and sound change exactly when the line starts), not an implementation detail. Shipping it unilaterally would be
a design change by stealth.

## 4. Files changed

- `tools/llm/latency_breakdown.py` — new: replays a transcript record's exact request against a llama-server and
  times every landmark in §1.1; `--order {docs,music_fx_beats_first,beats_first,say_first,alphabetical}` and
  `--no-cache` are the measurement variants; writes the JSON the tables above are derived from. `visible_ms`
  models `Safety._drain` on the compact views (a Python mirror of `SafetyText.gd`, tables pinned by a test).
- `tests/test_latency_breakdown.py` — 37 cases: schema-order restoration (the transcript copy is alphabetical),
  the ordering patch against a **CRLF** fixture and a real recorded prompt, the `say` landmark under the
  grammar's whitespace and inside JSON escapes, the compact-holdback model (including the row-0 example), the
  record loader, the summary statistics, and stub-SSE cases that drive `run_turn` end to end (split key, short
  `say`, escaped quote, dead server).
- `tools/promptlab/lab.py` + `run.py` — `--order` on the lab runner, and the wire property order is now a named
  constant pinned to `TurnSchema.DOCS_02_PROPERTY_ORDER` by `tools/promptlab/tests/test_promptlab.py`, so
  DCR-1's quality A/B cannot silently measure the old order.
- `tools/llm/README.md` — §3 documents the harness, the compact-holdback landmark, the CRLF ordering patch, and
  the CUDA gotcha I hit: a CPU-only extraction starts happily with `-ngl 99` and silently decodes at 11 tok/s.
- `production/handoffs/media/P2.26/*.json` — the committed measurement artifacts (12 files, 242 KB).

## 7. Deviations from the design bible

### Accepted deviation (D13, restated)

The `< 1.0 s` first-beat target is only meaningful with a GPU on the wire. Measured (medians of 6 turns, RTX
4050 at 53.3 tok/s): **1.1575 s** on screen with the shipped order (warm prefix), **1.489 s** cold KV, and
**0.909 s** with DCR-1's order — with the caveat that the DCR-1 median's p95 is 1.431 s (one pretty-printed
turn; §1.5). On a CPU-only host the measured floor is **2.408 s** with the `say` field first and every other
lever pulled (0.887 s of it is the safety holdback), and the shipped path is **6.037 s**. Proposed wording for
docs/09 / the phase doc: *"First beat on screen < 1.0 s median on the RTX 4050; the CPU-only host is a dev
fallback with a ~6 s first beat and is not release hardware."* The AC itself stays as written — do **not** fold
"with the schema order of DCR-1" into it unless DCR-1 is accepted in the same producer decision; otherwise the
record is this 1.1575 s miss plus DCR-1.

### DCR-1 — schema order: `music, fx, beats, read, inner, mood, memory, action`

- **Doc + code:** docs/02 **§1** (the "Field order matters" paragraph and the JSON example), **§1.1** (field
  table order), **§3** (the required property order), **§4** (the latency budget — see the DES-1 restatement
  below), docs/08 §5 (`rules.md` "Respond ONLY with JSON in this exact order"); `TurnSchema.DOCS_02_PROPERTY_ORDER`
  + `CANONICAL_PROPERTY_ORDER`, `Director.gd:378`, `game/data/prompts/rules.md`, the **fixtures** (not the
  assertions) in `game/tests/IncrementalJsonTest.gd:262-300`, and `tools/promptlab/lab.py:125-142` +
  `run.py` (the quality gate must send this order — see DES-2).
- **Docs/02 §4 restatement (DES-1).** The current text — *"first beat arrives in ~0.6–0.9 s when streamed
  (`read` + `inner` ≈ 30 tokens)"* — is contradicted by this ticket's own data: `read`+`inner` are **19**
  tokens, the shipped pre-say prefix is **48–49**, and the first beat measures **1.1575 s** on screen. Proposed
  replacement: *"**Latency budget (RTX 4050, measured):** full turn ~2.3 s median non-streamed; first beat on
  screen in ~0.9 s median when streamed under the DCR-1 order (pre-say prefix ≈ 30 tokens: music, fx, beat
  head; `read` + `inner` are 19 tokens and no longer precede the line) and ~1.16 s under the shipped order.
  The CPU-only dev host measures ~6.0 s. Typewriter speed 35–45 chars/s hides the rest."*
- **Why this order and not `beats` first:** it is the smallest reorder that clears the AC median. CUDA
  first-on-screen 1157.5 → **909 ms** (−21 %), CPU 6036.5 → 4571 ms. `music`/`fx` stay ahead of the beats, so
  the docs/02 §1 property ("the face and sound change exactly when the line starts") is preserved numerically:
  `music` closes **466 ms** before the first `say` char in this order, versus **503 ms** today (four turns
  each, RTX 4050). `beats` first puts it **+1278 ms after** the line starts.
- **Compact JSON clause (DES-6).** One turn under this order emitted pretty-printed JSON (`{\n"music": "calm",`
  …): 59 pre-say tokens instead of 30–34, first `say` 1246 ms instead of 706–764, on-screen 1431 ms instead of
  853–922. `rules.md` gains one sentence — *"Output the turn as one line of compact JSON: no newlines, no
  indentation."* — and the gate measures the pre-say token count (a turn above ~40 tokens is a whitespace
  failure). Without that clause the order's **p95** misses the AC even though its median clears it.
- **What it does cost:** `read` and `inner` arrive after the first beat's text. No display consumer needs them
  earlier (`read` only feeds path scoring and trigger backup, `inner` is only shown from stage 2 leaks), but
  **`inner`-first was itself a validated quality choice** (docs/02 preamble: "with `inner` first … 100 % valid,
  94 % emotion fit"), so quality must be re-measured, not assumed.
- **Gate:** design review + a prompt-lab A/B run through the game's own schema order:
  `python3 tools/promptlab/run.py --order music_fx_beats_first` (the lab's property order is pinned to
  `TurnSchema.DOCS_02_PROPERTY_ORDER` by `tools/promptlab/tests/test_promptlab.py`, so the A/B cannot send the
  old order with the new prose) scored for `read_accuracy`, `first_beat_fit`, `valid` and rules adherence
  (`music` 'keep' unless a change was offered, `cue` from the offered list, compact JSON), against
  `tools/promptlab/results/2026-11-03_v1.json`. If quality regresses, the fallback is
  `beats, read, inner, music, fx, …` (0.669 s median) with an explicit acceptance that music/fx trail the line
  by ~1.28 s.
- **Not proposed:** `say` first inside the beat (0.464 s) — it breaks the sprite-before-text timing outright and
  is quoted in §1.5 only as the upper bound of the lever.

### DCR-2 — prompt layout: make the prefix cacheable (docs/08 §1 vs docs/07 §3.1)

docs/07 §3.1 promises "system prompt prefix is stable within a scene → prompt caching", but docs/08 §1 puts the
per-turn `[scene] [memories] [events]` **inside** the system message, ahead of `[rules]` and the whole history.
Measured consequence (§1.4, recorded turns and a controlled probe): a new **memory fact** moves the first
differing character to char 1617 of the 3439-char system message and the server reuses **0** tokens
(prompt_n 1298/1449, prefill 10.9–12.2 s CPU); a **history-window slide** diverges after the system message and
reuses 944–971 tokens (prompt_n 434–567). One character changed deep inside the system message costs the whole
cache; a clause appended to the last user message reuses 1211 of 1237.

- **Carrier (DES-4).** `PromptBuilder._messages` emits `[system][history…][user(player)][assistant(prefill)?]`.
  The trailing block has to be a **`user`-role message** between the history and the player line:
  `[system(fixed)][history…][user(turn block)][user(player)][prefill?]`. A second **system** message is not an
  option — the pinned Qwen3.5 template raises `System message must be at the beginning.` (verified: HTTP 500 on
  the CUDA server for exactly that shape). Two consecutive `user` messages are accepted by the same template
  (verified: HTTP 200, the model answered the trailing line). The block must **not** be folded into the player
  message: `TurnContext._prior_history` drops a trailing `user` entry only when its text equals the player line
  exactly, so folding would resurrect the P1.08 duplicate-user bug. `_prior_history` itself needs no change —
  it inspects the history array's tail before the block is added — but the block must never be persisted into
  the Director's `history` (it is per-request only), and a `PromptBuilderTest` must pin the message order and
  the duplicate-user guard together.
- **What the layout buys, and what it does not (DES-3).** Warm turn-to-turn medians gain ~0 (as measured). A
  memory-fact turn stops paying the full re-prefill: everything before the trailing block stays cached, so the
  cost drops from 1298–1449 tokens to the block itself. A history slide still invalidates from the slide point
  (434–567 tokens) — that needs a cache-aware history, a separate ticket. The **cold** first beat does not
  benefit: §1.3's cold measurement is `cache_prompt=false`, which re-evaluates the whole prompt regardless of
  order. The reachable version of that win is "first beat of a new session on a server already warmed with the
  fixed layers", which is the warm-up request in §8.2, not this DCR.
- **Quality gate.** Moving `[rules]` ahead of the history changes instruction recency (today the rules are the
  last thing the model reads before the exchange). Gate: the same prompt-lab A/B as DCR-1 (real schema order),
  scored for `read_accuracy`/`first_beat_fit`/`valid`/rules adherence, plus a cache regression test — two
  consecutive turns of a recorded session must keep `prompt_n` below ~200 by construction (§8.3).
