# Handoff — P2.26: first-beat latency — measured, attributed, and priced

## Round 1  (2026-11-04, agent: commandcode)

### Summary

The 7.5 s first beat is **not** model time-to-first-token. It is the ~48 JSON tokens the model must emit
*before* the first `say` character, paid at the 4B model's decode rate. Replaying the exact prompts 39 real
production turns sent (`production/playtests/P1/transcripts`), the shipped path medians are **5.23 s** to the
first usable `say` and **5.92 s** to the first character the screen may show on the CPU host, versus
**1.02 s / 1.16 s** on a real CUDA host (RTX 4050, CUDA 13.4 build, `-ngl 99`). The breakdown closes: 72.6 %
pre-say decode, 15.6 % prompt prefill, 11.6 % the safety filter's 34-char holdback, 0.2 % HTTP.
Moving `read`/`inner` behind `beats` — prototyped and measured, **not shipped** — takes CUDA to 0.70 s / 0.86 s
and the CPU host to 3.81 s / 4.47 s, i.e. **the prescribed AC clears on the target hardware** while every
docs/02 §1 timing property (music/fx and the beat's feeling/cue before its text) still holds. Because that
reorder changes docs/02 §3 and a pinned test, it goes out as **DCR-1**, with the numbers below. No game code
changed this round. The CPU-host path cannot reach 1.0 s at all (its floor is the safety holdback plus six
tokens), so D13's deviation is restated as hardware-qualified.

## 1. Where the time goes (measured, not modelled)

### 1.1 The chain these numbers measure

```
POST ─► headers/queue ─► prefill (prompt tokens) ─► first token ─► pre-say decode
     ─► first `say` character ─► safety holdback (34 chars) ─► first character on screen
```

Each landmark is one clock (`tools/llm/latency_breakdown.py`), and the last two are the game's own:
`Safety._holdback = max(16, _max_phrase+1) = 34` chars (`game/autoload/Safety.gd:12,289`; the suite prints
"stream holdback: 34 chars"), after which `_drain` also trims to a token boundary; `TextBox.say_chunk` hands
the released text to the 40 cps typewriter, so the *first* character appears on the next frame
(`game/scenes/ui/TextBox.gd:52-57,76-84`, `game/scenes/ui/Typewriter.gd:19`).

Inputs: `session 1`'s six consecutive recorded prompts and their recorded JSON schema, re-sent verbatim
(`messages` + `response_format` + that turn's `sampling` row + `max_tokens 600`), to
`Qwen3.5-4B-Q4_K_M.gguf`, `-c 8192 -np 1`, `cache_prompt=true`. The schema order is restored to docs/02 §3 —
the transcript's copy is alphabetical because `TranscriptLogger.gd:300` calls `JSON.stringify` with its default
`sort_keys=true` (S3 finding, §8.6).

### 1.2 Shipped order, warm prefix — CPU host vs CUDA (medians of 6 turns)

| term | CPU host (6 threads, 11 tok/s) | CUDA (RTX 4050, 54 tok/s) |
|---|---|---|
| HTTP + queue (first byte) | 12 ms (0.2 %) | 15 ms (1.3 %) |
| prefill of 69–83 new tokens | 922 ms (15.6 %) | 118 ms (10.1 %) |
| pre-say decode, 48 tokens | 4295 ms (72.6 %) | 886 ms (76.4 %) |
| **first usable `say`** | **5229 ms** | **1018 ms** |
| screen-visible safety holdback (34 chars) | 688 ms (11.6 %) | 140 ms (12.1 %) |
| **first character on screen** | **5918 ms** | **1159 ms** |
| whole turn (all beats + tail fields) | 11273 ms | 2362 ms |

Per-token cost: 88.8 ms (CPU) vs 18.5 ms (CUDA) — the decode rate is the entire hardware difference
(11.0 vs 54 tok/s), not the prompt.

### 1.3 First beat of a session (cold KV, `cache_prompt=false`; the whole 986-token prompt)

| | CPU host | CUDA |
|---|---|---|
| prefill of 986 tokens | 8582 ms (116 tok/s) | 460 ms (2143 tok/s) |
| first usable `say` | 12416 ms | 1320 ms |
| first character on screen | **13175 ms** | **1478 ms** |

So the *first* beat after a server launch is 2.2× the steady-state cost on the CPU host and 1.3× on CUDA: the
fixed prompt is 986 tokens (persona 173 + rules 200 + glosses 219 + stage_0 254 + scene/memories/enums/player ≈ 140).

### 1.4 What the 39 recorded production turns say (`production/playtests/P1`, CPU host)

| metric | median | p95 | max |
|---|---|---|---|
| first byte | 21 ms | 274 ms | 358 ms |
| first token (prefill + ttft) | 945 ms | 5024 ms | 12437 ms |
| first usable `say` | **5359 ms** | 9679 ms | 17218 ms |
| … of which pre-say decode (`first_say − first_token`) | 4362 ms | 7114 ms | — |
| whole turn | 12041 ms | 21052 ms | 23481 ms |
| prompt tokens re-evaluated (the part the KV cache missed) | 68 | 567 | 1449 |

My replay of the same session reproduces this within 130 ms (5229 vs 5359 ms), so the harness is faithful.

**The pre-say token census** (server `/tokenize`, 34 recorded outputs): **48 tokens** median, spent on
`{"read":"…",` 6 · `"inner":"…",` 13 · `"music":"…","fx":"…",` 10 · `"beats":[{"feeling":"…","intensity":N,"cue":"…","say":"`
21.5 (the pieces sum to ~50 because the segments' boundary tokens are shared, the prefix as a whole is 48). The
timing agrees exactly: 4362 ms ÷ 90.3 ms/token = 48.3 tokens.

**The prefill cliffs.** Prefill is 13.6 % of all turn time (70.6 s of 518.9 s) but lands unevenly: 6 of 39 turns
paid 3.9–12.2 s because the KV prefix was invalidated, and the cause is the *layout*, not the length:

- turns 5→6 and 8→9 (session 1): a new **memory fact** landed. `memories` sits before `rules` in the system
  message, so the first differing character is at char 1617 of the 3439-char prompt (turn 6) and char 1682 of
  3473 (turn 9) → prompt_n 1298/1449, prefill **10856 / 12235 ms**.
- turns 11→12 and 12→13 (s1) and 12→13 (s2): the 12-exchange **history window slid**, so the first differing
  character is the start of the history → prompt_n 434–567, prefill **3973–5011 ms**.

### 1.5 The order lever — measured prototypes (same prompts, same servers)

| schema order (top level) | pre-say tokens | CPU: first `say` / on screen | CUDA: first `say` / on screen |
|---|---|---|---|
| `read, inner, music, fx, beats, …` (shipped) | 48 | 5229 / 5918 ms | 1018 / 1159 ms |
| `music, fx, beats, read, inner, …` | 30 | 3806 / 4466 ms | 704 / **863 ms** |
| `beats, read, inner, music, fx, …` | 21 | 2851 / 3512 ms | 556 / 707 ms |
| `beats[{say, feeling, …}], …` (say first) | 6 | 1497 / 2210 ms | 293 / 422 ms |
| alphabetical control (`action` first) | 27 | — | 685 / 888 ms |

Per-token cost is unchanged (19.2–24.7 ms CUDA, 89.5–94.8 ms CPU); only the token count moved.

The **control run** is what proves the lever is the *schema* order and not the prompt's ordering sentence: with
the transcript's sorted copy on the wire the model emitted `{"action":"none","beats":[{"cue":"giggle",…` even
though the system message says "Respond ONLY with JSON in this exact order: read, inner, music, fx, beats…".

### 1.6 Where `music`/`fx` land (why the row above matters)

`music`/`fx` are at decoded token 21 of 120 in the shipped order, token 1 of 120 in `music_fx_beats_first`, and
85 of 116 when `beats` goes first — i.e. at 54 tok/s that last variant makes the background music arrive **~1.6 s**
after her line starts. That is why DCR-1 recommends `music, fx, beats, read, inner, …`, not `beats` first.

### 1.7 The terms that are *not* the problem

- **Model ttft.** First token is 132 ms (CUDA) / 934 ms (CPU) *including* prefill of the new tokens; there is no
  queue to speak of (one slot, one in-flight turn, first byte 12–15 ms).
- **Safety scan cost.** `tools/test.sh` measures the streaming filter at **560 µs per `say_chunk` call** over
  11271 calls; the first beat crosses the holdback in ~10 chunks, i.e. **< 6 ms** — 0.1 % of the first beat.
  The filter's *holdback* is the real safety term (140 ms CUDA / 688 ms CPU), and it is a correctness feature,
  not a bug to shave.
- **Typewriter.** 40 cps, clamped 35–45 (`Typewriter.gd:19,31-34`); the first character is not delayed by it (a
  60-char line still takes 1.5 s to finish appearing — visible pacing, outside this ticket).

## 2. Root cause and the honest verdict

**Root cause:** the `say` text is the 5th field of the object and the 4th field of the first beat, so the model
must decode ~48 tokens of `read`, `inner`, `music`, `fx` and the beat head before the first displayable
character exists. At 11 tok/s (CPU host) that is 4.3 s; at 54 tok/s (RTX 4050) 0.89 s. Adding the prompt and
the holdback gives 5.92 s / 1.16 s.

**Against the AC** ("first beat on screen < 1.0 s median on the RTX 4050"): the shipped order measures
**1.159 s** — a 16 % miss, not a 7.5× one. With DCR-1 (`music, fx, beats, …`) it is **0.863 s** (median; p95
1.04 s) and with `beats` first **0.707 s**. On the CPU host no design meets it: the measured floor with `say`
first is **2.210 s**, and 0.71 s of that is the safety holdback alone.

**D13's headline number is a different prompt.** `bench_p121.py` sends a hand-written system prompt, not
`PromptBuilder`'s output, and its pre-say prefix ran ~81 tokens; the shipped prompt's median is **5.36 s**
(39 recorded turns). The "1.86 s CUDA" in the journals fits the same arithmetic: 1.16 s warm plus its
~33 extra pre-say tokens at 18.5 ms ≈ 1.77 s, plus a colder prefix.

## 3. What is cheap, and what needs a decision

| Lever | Effect (measured) | Cost | Verdict |
|---|---|---|---|
| Schema order: `music, fx, beats, read, inner, …` | CUDA 1159 → **863 ms** (−26 %); CPU 5918 → 4466 ms | ~12 lines + docs/02 §3 + 1 pinned test | **DCR-1**, recommended. Clears the AC on CUDA and keeps every docs/02 §1 timing property. |
| Schema order: `beats` first | CUDA 707 ms | same, but music/fx trail the first line by ~1.6 s | Not recommended; kept as the measured upper bound. |
| Prompt-layout cache stability | median ~0; removes 4–12 s cliffs and most of the 8.6 s cold prefill | PromptBuilder layout + docs/08 §1 | **DCR-2** (§7). Cheap to implement, delivers what docs/07 §3.1 already promises. |
| Warm-up request at launch | first beat of a session only: CUDA 1478 → ~1159 ms, CPU 13175 → ~5918 ms | one 1-token POST when the server is ready | Follow-up (§8.2). No doc change, needs a prompt-layer seam. |
| Cap `inner` at 60 chars (now ≤ 90) | ~4–6 tokens off the long tail (−0.1 s CUDA) | data + docs/02 §1.1 | Not worth a round on its own; fold into DCR-1 if it happens. |
| CPU thread tuning (`-t 12`) | **worse**: 22–62 s vs 9.0 s per 120-token reply (2.4–6.9× slower, SMT/thermal) | — | Rejected, measured. |
| Speculative decoding / smaller model | would cut the decode term 1.5–2.5× | a local draft GGUF (cannot be committed) | Follow-up (§8.4). |

**No game code was changed.** The lever that clears the AC contradicts docs/02 §3's field table and
`game/tests/IncrementalJsonTest.gd:293-300`, which pins "music/fx and the beat's feeling/cue land before that
beat's text" — a design property (the face and sound change exactly when the line starts), not an
implementation detail. Shipping it unilaterally would be a design change by stealth.

## 7. Deviations from the design bible

### Accepted deviation (D13, restated)

The `< 1.0 s` first-beat target is only meaningful with a GPU on the wire. Measured: 1.159 s (shipped order, RTX
4050, warm prefix), 1.478 s (cold KV), 0.863 s with DCR-1. On a CPU-only host the measured floor is **2.210 s**
with the `say` field first and every other lever pulled (0.71 s of it is the safety holdback), and the shipped
path is **5.918 s**. Proposed wording for docs/09 / the phase doc: *"First beat on screen < 1.0 s median **on a
CUDA host with the schema order of DCR-1**; the CPU-only host is a dev fallback with a ~6 s first beat and is
not release hardware."*

### DCR-1 — schema order: `music, fx, beats, read, inner, mood, memory, action`

- **Doc + code:** docs/02 §1 (the "Field order matters" paragraph and the JSON example), §1.1 (field table
  order), docs/08 §5 (`rules.md` "Respond ONLY with JSON in this exact order"); `TurnSchema.DOCS_02_PROPERTY_ORDER`
  + `CANONICAL_PROPERTY_ORDER`, `Director.gd:378`, `game/data/prompts/rules.md`, and the order asserts in
  `game/tests/IncrementalJsonTest.gd:262-300`.
- **Why this order and not `beats` first:** it is the smallest reorder that clears the AC. CUDA first-on-screen
  1159 → **863 ms** (−296 ms, −26 %), CPU 5918 → 4466 ms. `music`/`fx` stay ahead of the beats, so the docs/02 §1
  property ("the face and sound change exactly when the line starts") is preserved literally — measured: `music`
  is at decoded token 0 of 120 in this order, versus token 85 of 116 when `beats` goes first, which would delay
  the background music by ~1.6 s.
- **What it does cost:** `read` and `inner` arrive after the first beat's text. No display consumer needs them
  earlier (`read` only feeds path scoring and trigger backup, `inner` is only shown from stage 2 leaks), but
  **`inner`-first was itself a validated quality choice** (docs/02 preamble: "with `inner` first … 100 % valid,
  94 % emotion fit"), so quality must be re-measured, not assumed.
- **Gate:** design review + a prompt-lab A/B (`read_accuracy`, `first_beat_fit`) against
  `tools/promptlab/results/2026-11-03_v1.json` before the order ships. If quality regresses, the fallback is
  `beats, read, inner, music, fx, …` (0.707 s) with an explicit acceptance that music/fx trail the line.
- **Not proposed:** `say` first inside the beat (0.422 s) — it breaks the sprite-before-text timing outright and
  is quoted in §1.5 only as the upper bound of the lever.

### DCR-2 — prompt layout: make the prefix cacheable (docs/08 §1 vs docs/07 §3.1)

docs/07 §3.1 promises "system prompt prefix is stable within a scene → prompt caching", but docs/08 §1 puts the
per-turn `[scene] [memories] [events]` **inside** the system message, ahead of `[rules]` and the whole history.
Measured consequence: one new memory fact moves the first differing character to char 1617 of 3473 and
re-prefills 1298–1449 tokens (10.9–12.2 s CPU); a history-window slide re-prefills 434–567 tokens
(4.0–5.0 s). Proposed: keep `[persona][player][stage][path][rules]` (the fixed ~846 tokens) first, then the
history, then a trailing per-turn block carrying scene/memories/events/offered values + the player line. The
median first beat gains nothing; the p95 loses its 5–12 s tail and the cold first beat loses most of its
8.6 s (CPU) / 0.46 s (CUDA).

## 8. Open questions / follow-ups

1. **DCR-1 decision + quality A/B** (SYS + QA): replay `tools/promptlab/sets/*` under `music_fx_beats_first` and
   compare `read_accuracy`/`first_beat_fit` to `2026-11-03_v1.json`. If quality holds, the implementation is
   ~12 lines plus the order fixtures.
2. **Warm-up request at launch** (SYS/ENG): `PromptBuilder` gains a "fixed layers only" build; the LLM facade
   sends it with `max_tokens=1` once `/health` answers, so the first beat of a session does not pay the 986-token
   prefill (measured gap: CUDA 1478 → 1159 ms, CPU 13175 → 5918 ms). This is the "keep-alive warm" option and it
   needs no doc change.
3. **DCR-2 implementation + a cache regression test** (SYS): a unit test that two consecutive turns of a recorded
   session keep `prompt_n` below, say, 200 by construction.
4. **Decode side** (LLM): speculative decoding with a small local draft GGUF cuts the 76 % term; needs a local
   artifact and a `LlamaServerProcess` flag path, so it is its own ticket.
5. **D13 provenance** (producer): cite the shipped path's measured 5.36 s (39 turns) instead of the P1.21 bench's
   7.5 s, which used a hand-written prompt; and hardware-qualify the AC as in §7.
6. **S3 — transcript schema provenance** (SYS): `TranscriptLogger.gd:300` writes with `JSON.stringify`'s default
   `sort_keys=true`, so a stored record cannot reproduce the request it describes (the wire order is lost). Same
