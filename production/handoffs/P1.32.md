### Summary
Transcript redaction is now record-wide instead of `output`-only. A new `TranscriptRedactor` (wired by
`Director._wire_safety_redactor`) scans three model-text surfaces through the same `Safety` filter the
display uses — the raw `output`, every text-bearing `applied_events` payload (`field`/`beat_field`
values, and the `say_chunk` stream joined per reply), and the assistant history quoted back inside
`prompt`. Engine vocabulary (`read`/`music`/`fx`/`action`/`feeling`/`cue`, `intensity`, `mood`) and
numbers stay byte-identical, and a filter-less build still fails closed to bars plus
`meta.redaction = "unavailable"`. The scan is the filter's stateless whole-text API
(`SaySafetyGate.scan_text`), so a transcript write cannot read or write the streaming scanner's carry:
one payload is one utterance structurally, and the next reply's display state is untouched.

The approved P1.16 round-2 cases are back on this branch (`test_photosensitive_wiring`,
`test_ambience_forwarding`, the 25-frame capture settle), verified green on current main wiring
(P1.31's `_scan_opening_say`, P1.19's safety seam) with no adaptation needed. The restore keeps P1.21's
`test_vram_usage_budget_under_800mb`, which merge `50752b7` had also carried in — see finding **B2**.

### Deviations from the design bible
None. Two deliberate implementation choices worth naming (neither contradicts a doc):
1. **Stateless scan, not the streaming gate.** `SaySafetyGate.scan_text()` calls the filter's
   `filter_text`, so (a) two payloads can never share a match window — the reply boundary is
   structural, not a call — and (b) a transcript write cannot mutate the streaming scanner's
   `_pending`/carry that the next reply's display depends on. Same filter, same lists, same bars.
   Pinned by the existing seam tests, which still pass untouched: `test_replay_turn_marks_the_reply_boundary`
   asserts a whole `replay_turn` — transcript logging included — adds exactly **one** `end_utterance`
   call, and `test_say_chunks_are_scanned_once_and_safety_drives_beat_boundaries` asserts
   `beat_scans == 1` and `end_say_calls == begin_say_calls`. The transcript pass opens no beat and
   cuts no carry.
2. **`prompt` scanning covers assistant messages only.** PromptBuilder stores assistant history as
   spoken text (docs/08 §1), i.e. model output, so it is scanned; the system prompt is authored data
   and the user line is the player's own words (docs/02 §8 exempts player-typed text) and stays
   verbatim for the corpus.

- Side effect worth knowing: the transcript scan runs through `Safety.filter_text`, which appends to
  `user://debug/redactions.jsonl` and requests the FX glitch once per barred surface (the old
  `output`-only pass did the same once). Harmless in dev, but a `quiet` scan flag on the filter would
  keep the tuning log free of transcript duplicates — propose a P2 ticket for SAFE if it matters.
- `say_chunk` grouping assumes one record == one reply (true: `_log_turn_record` runs per turn and
  `_start_turn` cuts the carry with `end_utterance`). If a future path ever logs two replies in one
  record, it must split the chunk stream itself.
