# Handoff — P2.02: Stage machine 0–5 from instability thresholds; diegetic transition event (2–3 s glitch)

## Round 1  (2026-11-04, agent: commandcode)

### Summary
The docs/01 §3 stage machine now has one definition and one data source. `game/llm/Stages.gd` reads
`game/data/stages.json` (bands `[0,15,30,50,70,90]`, the six stage names, the transition spec and the
post-transition EVENT line per stage) and answers "which stage is this Instability value in"; `GameState`
keeps the live stage, the monotonic rule and the signals. A crossing now emits `stage_transition(previous,
current, spec)` **once** — the guard is the stage-rise itself, so repeated writes inside a band are silent, a
two-band jump is one event, and a save restore emits none — and queues exactly one docs/08 §6 `EVENT: …` line
that the Director drains into the **next** turn's prompt. The 2–3 s window, fx and cue are data; the duration
is clamped to the doc's window by the loader.

### Deviations from the design bible
- **The transition bypasses the docs/02 §5 fx budget and the docs/02 §2.3 stage gate.** docs/01 §3 makes the
  transition diegetic on *every* stage change, while the fx table gates `glitch` at stage 3 with a
  1-per-2-turns cap. Implemented as its own engine event (`stage_transition`) rather than `FX.trigger()` so a
  stage-1 crossing still glitches. No DCR: docs/01 §3 and docs/02 §2.3 govern different effects (the
  transition vs. a beat's mood), and the data file records the distinction.
- **The transition instant is the Instability write, not the turn boundary.** The crossing happens inside
  `_refresh_stage()`, i.e. wherever Instability moves — the turn close today, the night roll-over in P2.19,
  a trigger spike in P2.08. The spec is emitted on that write so P2.03 can start its server restart inside
  the glitch window.
- **One EVENT line per crossing, not one per stage insight.** `docs/01` says she "often" comments afterwards;
  the AC requires the line, so every crossing queues exactly one, and the data prose is NAR-editable without
  a code change.
- **`STAGE_BANDS`/`STAGE_MAX` removed from `GameState`.** The brief named them as the data source; a GDScript
  `const` cannot be read from JSON, so their values moved to `game/data/stages.json` and their accessors to
  `Stages` (the P2.01 `Meters` precedent). All call sites are migrated; nothing else changed meaning.

### Open questions / follow-ups
- **P2.03 (LLM)** consumes `GameState.stage_transition`; the payload is
  `{"stage", "name", "duration_s", "fx", "cue"}` plus the signal's `previous`/`current`. The restart must fit
  inside `duration_s` (2.5 s shipped, clamped to docs/01 §3's 2–3 s).
- **P2.15 (ART)** draws `fx: "glitch"` for the window; the stage machine names the effect but owns no
  rendering, so the `Settings.photosensitive` / reduced-motion substitution belongs there (docs/02 §2.3).
- **P2.08 (triggers)** can use `GameState.queue_event()` for its TRIGGER lines — the queue guarantees
  next-turn delivery exactly once, but the Director now clears `_turn_events` *before* the telemetry hook, so
  hook lines survive (they did not before; no hook exists yet, so no behaviour changed today).
- **P2.19 (day/night)** gets the crossing for free through `advance_day()`; the night screen can read
  `pending_events` before the next prompt if it wants to show what changed.
