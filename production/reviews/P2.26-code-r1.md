### CODE-1 — `--system-order` is a silent no-op on every real record (S2)

`patch_system_order` looks for `"Respond ONLY with JSON in this exact order:\n"` (`:168`) and only rewrites a system message when that literal is present (`:179-180`). The real prompt is CRLF: the recorded system message is `'Respond ONLY with JSON in this exact order:\r\nread: …'` and `game/data/prompts/rules.md` has 11 CRLF pairs. Result: **0 of 39** records match, and the patcher returns all 39 prompts byte-identical — I called it directly on the first recorded turn and got `changed? False`. The two tests that cover it (`tests/test_latency_breakdown.py:101`, `:112`) pass only because the `SYSTEM` fixture at `:47` is hand-built with `\n`, a string that cannot occur in production. The tool's own worked example (`:28-31`) passes `--system-order`, so an operator following the docstring silently measures the *unpatched* prompt while believing the ordering sentence was repointed. This is the harness's only prompt-side variant, and its only guard certifies the broken behaviour.

Scope of the damage: the handoff's numbers survive (the committed variants are schema-order runs, and §1.5's control run is precisely the evidence that the sentence does not drive the output), but the flag must not ship silently broken. Even once matched, the replacement rewrites only the header line and leaves the list below it naming the shipped order — say so in the docstring, or rewrite the list too.

### CODE-2 — an escaped quote ends the `say` string early (S3)

The SSE delta carries the raw JSON text, so a `"` inside `say` arrives as `\"`. `closed = text.find('"', body_at)` (`:259`) stops at the escape's quote, so `say_closed_ms` is stamped and `say_chars` freezes at that position; when that position is below the holdback, the close fallback at `:276` reports the first-visible time as the chunk in which the *quote character* arrived. My stub server shows it: a 66-character line containing `\"hi\"` reports `first_say_ms 0, visible_ms 0, visible_chars 10`. Trigger: any replayed turn whose first `say` quotes something ("She said \"hi\"", dialogue quoting, etc.). No committed artifact is affected — I scanned all 11 files and 0 rows contain a backslash in `output` — so this round's figures stand, but the tool would silently under-report the first beat on such a turn.

### CODE-3 — `visible_ms` is a lower bound, not the filter's release point (S3)

`Safety._drain` cuts at `_compact_bound`, computed on the separator-free views (`Safety.gd:582-597,624-641`), and `_bound_of` keeps the last `_holdback` **compact** characters; a phrase prefix padded with spaces or punctuation therefore does not buy emission budget. The harness instead releases when the raw say body reaches 34 characters (`:270-274`), which happens earlier and is therefore optimistic. Concretely, on `cpu_docs` row 0 the 35th compact character is raw character 48; the row's own `say_curve` places raw 48 at 5718 ms while the artifact reports `visible_ms 5363`. That is ~4 tokens ≈ +0.35 s on this CPU row, and at 18.6 ms/token ≈ +75 ms on CUDA. Direction matters: the shipped path becomes a *larger* miss (≈6.27 s CPU / ≈1.24 s CUDA), and DCR-1's projected median moves 863 → ~0.94 s (still under 1.0 s) but its p95 moves 1.04 → ~1.11 s, so the handoff's "p95 1.04 s" claim no longer clears either. Rows whose `say` closes before the raw threshold (e.g. `visible_chars 33` in the DCR-1 artifact) are exact, because both paths fire at the beat close. Fix by counting compact characters (skip the separator classes like `SafetyText.compact_key`) plus the same trailing-token trim, or state the bound in the tool docstring, `tools/llm/README.md` §3.1 and handoff line 60.
