### CODE-1 — the reveal budget is not re-checked after the anti-repeat swap

`resolve_beat` applies the budget to the sprite `resolve()` returned (`:75-81`), then runs the anti-repeat swap (`:82-91`), then books `_reveals[sprite]` for the *final* sprite. `_sibling_for` returns `siblings_corrupt["30"] == "21"` (`game/data/casting.json`; table `tools/casting/build_casting.py:243`) without asking whether 21's budget (`"1 reveal per scene"`) is spent.

Consequences on the shipped data (probe A/B above):

- Off-path, stage 4–5, three consecutive **angry i3** (or **disgusted i3**) beats: 30, 30, **21** — the knife appears for a run that never took the YANDERE path — and the sequence cycles, so six beats show the knife twice (`ledger {30:4, 21:2}`).
- YANDERE, stage 4–5, angry i3: beat 1 is 21, beats 2–3 are the budget-substituted 30, and beat 4 is swapped straight back to **21** — with `budget_spent: "21"` in the same packet and the `knife_draw` / `stinger.mid` / `vignette_red` / `dread` entry effects (docs/10 §3) playing a second time. The sweep finds 144 such overruns (2 feelings × 2 stages × 6 paths × 6 occurrences per 18-beat sequence).

This contradicts `docs/03_EMOTIONS.md:38` ("Reveal budget: 1 per scene") and the note this patch itself generated into `docs/10_CASTING.md:185` ("`1 reveal per scene` gates the sprite itself"). The shipped `test_reveal_budget_is_one_per_scene` (`game/tests/SpriteResolverTiersTest.gd:97-108`) only resolves two beats in one scene, so it cannot see the swap.

```suggestion
	if _candidate_gated(sibling, tier, flags):
		return ""
	var cap := _reveal_cap(sibling)
	if cap > 0 and int(_reveals.get(sibling, 0)) >= cap:
		return ""
	return sibling
```

(Equally valid: re-run the cap test on the post-swap sprite in `resolve_beat` and fall through to the pre-swap face when it is spent. The table entry stays as documented art direction either way; `30 -> 21` remains reachable once per scene.)

### CODE-2 — the reduced-motion re-run keeps the scale, but nothing asserts it

`set_reduced_motion(true)` re-applies the current preset with the beat's scale (`Character.gd:192`), which is the fix this task claims ("`motion_scale` … kept across `set_reduced_motion`"). The only reduced-motion lean_in assertion is at **i2**, where `casting.motion_intensity["2"] == 1.0` — the old code (`_apply_motion(_motion)`) produces the same 1.15. Mutation M2 (drop the scale argument) leaves `CharacterSceneTest` at 18/18 PASSED, so a regression that silently returns every reduced-motion preset to the i2 baseline would ship.

```suggestion
	_char.set_feeling("suspicious", 3, 0)  # i3: 1 + 0.15 * 1.4, still static
	await get_tree().process_frame
	assert_vector(_lean_root.scale).is_equal_approx(Vector2(1.21, 1.21), Vector2(0.001, 0.001))
	_char.set_reduced_motion(false)
```

### CODE-3 — the Date path resolves once now, but no test says so

`Date.play_opening_beats()` resolves the beat itself and hands the packet to `apply_beat(packet)` (`Date.gd:225-235`), so the anti-repeat window and the reveal budget advance once per beat (`Character.set_feeling()` still re-resolves when called, `Character.gd:155-156`). Reverting the branch to the old `character.set_feeling(...)` call still passes both opening-beat tests (mutation M1), because they assert the resulting sprite (06 / 01) and the beat count, not the number of resolver passes — the two numbers agree for the shipped stage-0/1 openings, so the regression would only surface later as a skipped sibling or a pre-spent knife. The Director path already has this assertion (`game/tests/DirectorRoutingTest.gd:321-350`, "Exactly one resolver pass per beat"); the Date path should mirror it.

```suggestion
	var passes: Array = []
	var sink := func(p: Dictionary) -> void: passes.append(p)
	SpriteResolver.beat_resolved.connect(sink)
	_date.start_date()
	await get_tree().process_frame
	assert_int(passes.size()).is_equal(1)  # one opening beat in the stage-0 scenario
	SpriteResolver.beat_resolved.disconnect(sink)
```

## Design deviations / DCRs reviewed

The handoff lists five deviations. I checked each against the code and the bible; the code implements what the handoff claims.

1. **Sprite tiers are data and only the minimum gates a candidate** — `SPRITE_TIERS` (`tools/casting/build_casting.py:34-44`) matches the docs/03 §1 "Tier" column for all 31 sprites; `_candidate_gated` (`SpriteResolver.gd:218-221`) gates only path candidates and siblings, and `_resolve_excluding` falls through to the feeling's base cell (`:274-290`). Probe: `angry` st3 YANDERE = 17, `cold`/`confused` st3 AWAKE = 07/08, while st4–5 overrides land unchanged. The proposed docs/03 §3 step-3 text is still only in the handoff — the producer must schedule it (process, not a defect).
2. **`terminal climax only` scope** — the sprite is allowed from T3 (docs/03 §3.1 casts 30 at angry i3), while the `system` sting is withheld below stage 5 and `fx_below_stage5` degrades the visual (`SpriteResolver.gd:316-322`); `_reveal_cap` deliberately returns 0 for this wording (`:262-269`). Coherent reading; still an open doc question, as the handoff says.
3. **Motion amplitude is art direction** — `MOTION_INTENSITY` = 0.6 / 1.0 / 1.4, generated into `casting.motion_intensity` and into docs/10 §2; `Character._apply_motion` uses the doc's own i2 numbers (6 px hop, ±4 px shake, 10 px sink, 1.15 lean, 1 px tremble, 2 px twitch) scaled by the packet. `test_motion_sink_drops_and_darkens` breaks the i2/i1 baseline apart (10 px vs 6 px) and `test_motion_lean_in_zooms_toward_face` the whole 1.09/1.15/1.21 ladder.
4. **Corrupt-band siblings** — `SIBLINGS_CORRUPT` validation enforces the band, no self-target and the tier-start bound (`build_casting.py:330-337`); the probe found no cross-band swap and no forward jump (23 stays 23 at T2 because 29 is T3-only). The `30 -> 21` pair itself is documented art direction; it only becomes a bug through CODE-1.
5. **Amplitude applies to displacement, not breathe/freeze** — verified: `breathe` and `freeze` do not read `_motion_scale`, and reduced motion still cuts shake/drift outright rather than softening (`Character.gd:372-429`, `:446-471`).

## Summary

Two small test gaps (reduced-motion scale, Date single-resolution) are proven by mutation and can ship as S3. Fixing CODE-1 and adding the two assertions should turn this round.
