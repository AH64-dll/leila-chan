## What the new code does, checked line by line

- `game/llm/ProfileKeywords.gd:147-161` — the predicate is the three narrowings in the order the round-1
  report asked for: `?` first (`:150`), the "is the message" cap (`:152-155`, `dismissal_max_words` = 6 from
  `profile_keywords.json:36`), then the answer gate (`:156-157`), then the ≤`short_reply_words` branch with the
  whole-word exemption (`:158-161`). A phrase match still wins over the exemption inside the cap.
- `game/llm/ProfileKeywords.gd:93-100` — `classify()` normalises `last_question` once, passes
  `awaiting_answer`, and nests `ignored_questions` under the dismissal, so the two counters cannot drift apart.
- Turn ordering is right: `GameState.gd:417-426` classifies with the stored `last_question` from the
  *previous* turn and only then stores `question_in(turn_data)` for the next one; `Director.gd:749-753` is the
  only call site and it runs once per turn. The answer gate therefore reads the question the player is
  actually answering, and the current turn's question cannot leak into it.
- The data contract `game/data/profile_keywords.json:3` states all three rules and both caps;
  `tests/test_paths.py:180-203` pins the key set and `dismissal_max_words > short_reply_words`;
  `ProfileKeywordsTest:163` pins 6.
- The parser accepts only an integer 0…12 for the new cap and 0…6 for the old one (`:209-210`, `:246-252`);
  an invalid value disables that rule (0) instead of guessing, and `EMPTY_TABLE:26-32` carries the key so the
  fallback cannot miss it. Probed: cap `6` → 6; `0`, `-1`, `13`, `6.5`, `"6"`, `null` → 0.
- The new tests are genuine regressions: checked against `git show 581c768:game/llm/ProfileKeywords.gd`, the
  CODE-1/2/3 blocks, `test_caring_question_is_never_a_dismissal`, the terse-answer pair and
