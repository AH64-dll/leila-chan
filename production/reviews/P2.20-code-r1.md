## Findings

| ID | Sev | Where (file:line) | Problem | Suggested fix |
|---|---|---|---|---|
| CODE-1 | **S1** | `game/scenes/Date.gd:485-487` | The after-turn autosave is refused with `error:"busy"` whenever `turn_displayed` fires synchronously from inside the Director's turn completion, and the Date discards the return value — the mid-date save the task exists for is then silently never written (data loss on a quit). | Defer the write one idle frame, past `_turn_in_flight` (below). |
| CODE-2 | S3 | `game/scenes/Date.gd:208-212` | `_resumed` is set for any pending scene, so a save taken during her greeting (its `log.entries` is empty — the opening beats reach the ChatLog only as they drain) resumes into an empty scroll-back with the greeting suppressed. | Base the greeting skip on the restored log actually being non-empty. |

### CODE-1 — the per-turn autosave is dropped inside the Director's in-flight window

`Date._on_turn_displayed()` calls `SaveSystem.autosave(...)` at `game/scenes/Date.gd:487`. The signal it is
wired to is emitted from `ChatUI._maybe_close_turn()` (`game/scenes/ui/ChatUI.gd:270-280`), which
`ChatUI.end_turn()` (`:225-228`) calls **synchronously**; `TextBox.end_turn()` (`game/scenes/ui/TextBox.gd:117-129`)
itself emits `all_displayed` when the typewriter has nothing queued, which routes back into the same
`_maybe_close_turn()`. For a real model turn the caller is `Director._on_response_complete()`:
`chat_ui_node.end_turn()` at `game/autoload/Director.gd:786`, and only afterwards
`_turn_in_flight = false` at `:788` — the flag `Director.is_busy()` returns (`:189-190`).
`SaveSystem.save_to_slot()` refuses while that flag is set (`game/autoload/SaveSystem.gd:91-93`,
`return _fail("busy", …)`), and `Date` ignores the returned dictionary, so there is no log line, no retry and
no other write path for that turn.

The write therefore happens only when the typewriter still has unrevealed text at that instant. It is refused
when the writer is already drained, which is reachable three ways: the player fast-forwards her line with
`ui_accept` before the stream closes (`game/scenes/ui/ChatUI.gd:318-320` → `text_box.reveal_now()`), the last
beat finished revealing before the final chunk arrived (`Typewriter._maybe_advance_beat`,
`game/scenes/ui/Typewriter.gd:188-200`), or text is instant (`TextBox.set_instant` → `Typewriter.advance`
drains the whole queue each frame, `:56-58` + `:173-184`). `UITest.test_empty_turn_hides_indicator_and_drains`
(`game/tests/UITest.gd:388-402`) already proves `end_turn()` closes a turn with nothing queued. When the write
is refused, the `auto` slot keeps the last successful capture — the Date entry (`Date.gd:316`) or the greeting
close — so `Continue` loses every completed turn since, which is exactly the guarantee the class comment and
the handoff claim ("so Continue resumes the date the player actually left", `Date.gd:313-315`).

The suite cannot see it: `game/tests/SaveFlowTest.gd:62` emits `turn_displayed` by hand on the ChatUI, so
`Director.is_busy()` is false at that moment and the write succeeds. A test that drives one completed turn
through the Director (or that asserts `is_busy()` is false when the write lands) would catch the regression.

```gdscript
	# P2.20: the scene autosaves as it progresses, so a quit mid-date resumes
	# the log the player actually saw instead of replaying the date. Deferred:
	# the Director clears its in-flight flag only after ChatUI.end_turn()
	# returns, and every save is refused ("busy") while it is set.
	SaveSystem.autosave.call_deferred(SaveSystem.SCENE_DATE, _save_scene_data())
```

### CODE-2 — a resumed date suppresses a greeting the save does not contain

`Date._resume_from_save()` sets `_resumed = true` for any non-empty pending scene (`game/scenes/Date.gd:212`),
and `start_date()` then takes the resume branch, emits `opening_beats_finished` and never calls
`play_opening_beats()` (`:304-312`). The save it resumes was written at the end of that same `start_date()` —
`SaveSystem.autosave(...)` at `:316` — *before* the greeting can be in the log: her opening lines reach the
ChatLog one beat at a time, from `ChatUI._on_beat_displayed()` (`game/scenes/ui/ChatUI.gd:260-263`) as the
typewriter drains them. A save from that window therefore carries `log.entries == []`, and on load
`SaveSystem._flush_pending_log()` returns early for an empty array (`game/autoload/SaveSystem.gd:353-357`), so
the resumed Date's ChatLog stays empty while the greeting is suppressed: the player quits during her first line,
presses Continue, and gets a silent date with a blank scroll-back. The comment's premise ("the player already
saw it", `Date.gd:305-306`) is only true once the greeting has actually been logged.

```gdscript
	_saved_turn = int(pending.get("turn", 0))
	# A resumed date skips the greeting only when the restored log carries it:
	# the on-entry autosave lands before the opening beats reach the log, so a
	# save taken during the greeting has an empty log and must play it.
	var log_node: Variant = chat_ui.chat_log if chat_ui != null else null
	_resumed = (
		log_node != null
		and log_node.has_method("entry_count")
		and int(log_node.call("entry_count")) > 0
	)
```

## Summary

The bytes layer is strong: the envelope (format, version, sha256 over the canonical payload), the tmp-file
rename, the tolerant listing and the `{ok, error, message}` contract all hold, and both acceptance criteria are
genuinely covered by tests that pass on my own run (19/19 focused, 608/608 project, lint and format clean).
One S1 blocks the merge: the after-turn autosave is wired to a signal the Director emits while its own
`is_busy()` flag is still set, so in the cases where the typewriter is already drained the only mid-date write
is refused and the failure is silently discarded — the "Continue resumes where the player left" guarantee the
task exists for does not hold. CODE-2 is the smaller resume edge: a save taken during the greeting restores an
empty log and then suppresses the greeting it never captured.
