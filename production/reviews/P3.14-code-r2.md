### CODE-1 detail — "one line per chat log" is true per scene, not per log

`Date` autosaves after each turn (`Date.gd:582`) and the autosave payload carries the log
(`SaveSystem.gd:181` `"log": {"entries": _read_log()}`); `_log_entries` copies `speaker_key`, `speaker`
and `text` verbatim (`SaveSystem.gd:405-426`), and `ChatLog.restore_entries` re-renders the stored
speaker (`ChatLog.gd:38-55`) — the "Leila" tag on the player's swapped line is data, not a rendering
decision. `Date._register_save_seam` registers that sink, and `SaveSystem._flush_pending_log` calls it on
load. A resumed Date therefore shows the swapped line **and** can add another: `_name_tag_swapped` is a
plain member (`ChatUI.gd:57`), and `ChatUI._turn_seq` — the roll's turn index — is never restored by
`Date` (only `ChatUI` increments it), so `player_tag_for(_turn_seq + 1)` replays from turn 1 with the same
`seed_base` (0 in production, a test knob at `CorruptionSession.gd:36`). My probe restored a one-swapped
-log into a fresh `ChatUI` and got `Leila` again at turn 2 — the same turn that fired before the save.

Severity is S3 rather than S2: the ordinary flow keeps the doc's "for one line", the repeat needs a quit
mid-date after the swap, and nothing in state, safety or the save envelope changes. It is the one
residual of r1's CODE-2/DES-6, whose dead data key **is** gone.
