### CODE-1 — the after-turn autosave is no longer swallowed inside the Director window

`Date._on_turn_displayed()` now calls `_autosave_scene.call_deferred("after turn")` (`game/scenes/Date.gd:520`).
The signal is emitted from `ChatUI.end_turn()` → `_maybe_close_turn()` (`game/scenes/ui/ChatUI.gd:329-332`,
`:378-388`), and `ChatUI.end_turn()` is called from `Director._close_turn_success()` at
`game/autoload/Director.gd:786`; `_turn_in_flight` is cleared only at `:788`, and `SaveSystem.save_to_slot()`
refuses while that flag is set (`game/autoload/SaveSystem.gd:91-93`). The deferred call is flushed after that
callback returns, so the write lands with `Director.is_busy() == false`. I checked the three r1 trigger paths: each
one closes the turn only via `_maybe_close_turn()`, which requires `_end_pending` to be set by `ChatUI.end_turn()`
— so the only in-window emission is the synchronous one inside `end_turn()`, exactly what the deferral moves past.
The handler also reads its result now: `disabled` stays silent (`Date.gd:245-246`), everything else is a
`push_warning` naming the reason (`:247`). `grep -rn "SaveSystem.autosave" game/` leaves exactly one call site,
inside `_autosave_scene` (`Date.gd:242`); `start_date()` (`:345`) and the deferred turn write both go through it,
so no call site drops the returned dictionary any more.

The regression test is the right shape: it streams one complete turn JSON from a backend that parks on its worker
thread until `release` (`game/tests/helpers/GatedLLMBackend.gd:13-27`, `OS.delay_msec()` runs off the main
thread), asserts `Director.is_busy()` is **true** when `turn_displayed` fires (captured by the lambda at
`SaveFlowTest.gd:188`, asserted at `:203`), asserts the file still holds only the greeting while the stream is open
(`:198`), then releases and asserts the next idle frame writes `[greeting, player line, her reply]` with
`scene.turn == 1` (`:204-211`). The positive control for the `_resumed` change is in
`test_loaded_log_is_restored_into_the_chat_log_and_history` (`:129`, `:134`).

### CODE-2 — a save taken before the greeting is logged no longer suppresses it

`Date._resume_from_save()` runs after `_register_save_seam()` (`game/scenes/Date.gd:160-161`), and
`SaveSystem.register_log_seam()` flushes a loaded log straight into `ChatLog.restore_entries()`
(`game/autoload/SaveSystem.gd:163-168`, `:353-357`), so `chat_log.entry_count()` is already the restored log when
the flag is computed (`Date.gd:224-227`). `start_date()` then only skips `play_opening_beats()` when `_resumed` is
true (`:333-339`). `SaveFlowTest.test_resume_plays_the_greeting_when_the_saved_log_is_empty` (`:140-160`) saves an
empty log, loads it, asserts `_resumed == false`, that `opening_beats_finished` is not emitted inside
`start_date()`, that `_opening_in_progress` is true, and that one entry lands once the greeting drains (reduced
motion, no wall-clock wait).
