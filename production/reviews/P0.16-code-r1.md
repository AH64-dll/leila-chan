## Findings

| CODE-1 | S2 | `tools/bridge/export_to_godot.py:279-290` and `:343-345` | Manifest-driven stale pruning trusts **every** string in `game/data/.bridge_manifest.json`. `ROOT / rel` is not contained to the bridge's destinations, and write mode calls `p.unlink()` on the result. A manifest entry such as `../victim.txt` (or an absolute path) deletes a file outside the repo; a merge or manual edit of the generated manifest can turn this into loss of tracked or uncommitted work. Scratch proof: `{"files":["../victim.txt"]}` → `_collect_stale` returns the outside file; the write loop deletes it (`victim still exists: False`). The normal generated manifest has only safe paths, so this is not hit on a clean run — but there is no containment guard. | Validate manifest entries as relative, non-empty strings whose resolved path is under `game/data/` or `game/assets/sprites/leila/` (the only bridge destinations), reject `..`/absolute entries, and skip/raise with a clear message. Add a pytest with an escaping entry and an absolute entry. |
| CODE-2 | S3 | `production/handoffs/P0.16.md:42`; `production/journals/P0/ART.md:25` | The claim that `.bridge_manifest.json` is "invisible to Godot's filesystem scan" / "Godot ignores dot-prefixed files" is false: after a fresh `godot --import`, `game/.godot/editor/filesystem_cache10` contains `.bridge_manifest.json::JSON::-1::…`. The manifest is inside the Godot project and may be swept into a future export filter; the stated rationale for placing it in `game/data/` does not hold. The handoff also says "renamed/dropped data files are detected as stale": a dropped **source** exits at the source-existence check (`export_to_godot.py:311-313`) before `_collect_stale`, leaving its destination in place — only renamed/replaced outputs are caught. | Move the manifest outside `game/` (e.g., `tools/bridge/.bridge_manifest.json`) or correct the handoff/journal and add an export exclusion when P0.11 defines the preset; reword the stale claim to "renamed/replaced outputs". |
| CODE-3 | S4 | `tools/art/leila_finish.py:1170-1188` | The new palette scan has no automated test, and because it appends every used-but-unlisted colour to `fx_derived`, `check_palette` becomes self-fulfilling after a regeneration: a generator regression that introduces a new colour would be silently admitted into the palette. The DCR documents this trade-off and the byte-stability evidence is good, so this is optional. | Add a scratch-px test that a planted colour lands in `fx_derived` and that a missing `px/` exits with the documented message — or accept the DCR's "true by construction" choice explicitly in the design review. |
| CODE-4 | S4 | `tools/art/leila_finish.py:1183-1185` | `cv2.imread` can return `None` for an unreadable/non-RGBA px file; `img[..., 3]` then raises `AttributeError` with no filename.
