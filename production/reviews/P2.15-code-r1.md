| CODE-1 | S3 | `game/scenes/character/Character.gd:885-894` | `_refresh_stage_fx()` decides the pass's visibility from the *instantaneous* uniform values, so a stepped cue that is momentarily at rest reads as finished. Normal-mode `flicker` sits at exactly `1.0` for 0.43 s of its 0.57 s timeline; if any other cue's end callback (`:273`, `:296`, `:776`, `:787`, `:799`, `:818`, `:835`) or a twitch's 2-frame split ending (`_process` → `_set_split(0.0)` at `:867-870`) calls it during a lit step, the pass is hidden and `_set_flicker_level` never re-shows it, so the rest of the cue (up to three dips) never renders. Reachable in normal play: twitches fire every 2-5 s in the `twitch`/`glitch` motion presets, which are the stage-3+ presets — a flicker during such a beat is cut ~75% of the time it overlaps (my probe: 0 of the remaining dip frames rendered). The same class of loss applies to any two pass-using cues that overlap, which `_restart_screen_tween`'s own comment (`:733-734`) says is intended. | Track which cues still hold a timeline and key visibility on that, not on a mid-cue value (snippet below); `clear_screen_fx()` must clear the same set. |
| CODE-2 | S3 | `game/scenes/character/Character.gd:309-324` | `clear_screen_fx()` kills the `shake` tween (`:311-317`) but never resets `_cam.offset`, so the camera stays at the last interpolated offset — measured 3 px horizontally in my run and in the handoff's stills. Suggested fix for CODE-1 (replace `_refresh_stage_fx` and add the set; each pass-using cue then sets `_live_fx["<name>"] = true` when it fires and ends with `tween.tween_callback(_end_fx.bind("<name>"))` instead of `tween.tween_callback(_refresh_stage_fx)` — shakes and the stage ramp keep the old callback):
```gdscript
## Cues whose timeline is still in flight. Visibility must not be derived from
## the uniforms alone: a stepped cue (`flicker`) sits at exactly 1.0 between its
## dips, so "all uniforms at rest" does not mean the cue has ended.
var _live_fx := {}


## Ends one cue: it no longer holds the pass on by itself.
func _end_fx(name: String) -> void:
	_live_fx.erase(name)
	_refresh_stage_fx()


## The pass is hidden whenever every uniform is at rest, so a clean stage pays
## no full-screen blit at all; any live effect shows it for its frames.
func _refresh_stage_fx() -> void:
	_stage_fx.visible = (
		not _live_fx.is_empty()
		or _desaturation > 0.0
		or _flicker < 1.0
		or _darken < 1.0
		or _vignette > 0.0
		or _glitch > 0.0
		or _split > 0.0
		or _bleed > 0.0
	)
```

## Summary
APPROVED. All three acceptance criteria are met with evidence I produced myself: the gate/cooldown table matches docs/02 §2.3–§5 row for row and both data and runtime suites pass; the photosensitive path is structurally clamped to ≥ 1/3 s per step with sampled-frame verification; and the single-pass composition is the correct fix for the screen-texture-stacking bug — my own captures show a lit flicker frame is pixel-identical to the stage-5 baseline (chroma 2.83 vs 2.84, aligned MAE 0.12) while a no-drain frame measures 12.28, and one pass holds 230-267 fps on llvmpipe with every effect live. The findings are non-blocking: CODE-1 is a real composition bookkeeping defect (a live flicker is cut when a twitch split or another cue's end lands on a lit step; reproduced), and CODE-2 is why the handoff's post-shake stills are 3 px off-centre — both are small fixes the producer may take now or ticket. One caveat on the 60 fps claim: the bench window is the shipped 384×688 framebuffer, and with `stretch/mode="canvas_items"` a larger (integer-scaled) window grows the 2D render target, so the pass cost scales with the window's pixel count — the Radeon p95 I measured (3.58 ms under load; 0.42 ms idle) absorbs a several-fold area increase, llvmpipe's ~5.2 ms would not.
