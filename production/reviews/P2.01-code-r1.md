### Formula, line by line

- docs/01 §2 `floor = peak − 15`: `Meters.gd:50-53` → `maxf(0.0, peak - ratchet_drop)` with `ratchet_drop = 15.0` (`meters.json:6`). The `maxf(0.0, …)` is correct for Instability's 0-100 range (an early peak has floor 0), not a retune.
- docs/01 §2 `+0.35 base +0.15 × (Fixation/100) −0.2 × (Lucidity/100)`: `Meters.gd:59-65` → `base + per_fixation*fix - per_lucidity*luc`, where `fix`/`luc` are the meters clamped to 0-100 and divided by 100. Values `0.35 / 0.15 / 0.2` come from `meters.json:8-11` and are doc-pinned. The clamp is a no-op for legal meters and only stops a bad caller bending the curve.
- docs/01 §2 `Per day: +3`: `Meters.gd:69-70` → `daily_burn = 3.0` (`meters.json:12`), applied once at the night roll-over in `GameState.gd:357-363`.
- docs/02 §1.1 `mood 3 ints −3..3, affection ×1.5, trust ×2, stress → instability ×0.6`: `Meters.gd:74-95` (`mood_limit`, `mood_scale`, `mood_delta` = clamp ±3 then scale); caller wiring in `GameState.gd:284-297`. `stress` maps to the Instability meter exactly as the doc's arrow says.
- docs/01 §2 "Moves by" caps `Affection ±5/turn`, `Instability ±3`, Trust uncapped: `Meters.gd:98-101` returns `5.0 / 3.0 / INF`, enforced on the per-turn running total in `GameState.gd:306-325` (two `apply_mood` calls in one turn share one budget; the existing CODE-3/CODE-7 tests still pass).
- No value was retuned, and `Meters.DOCS_TABLE` (`Meters.gd:20-30`) repeats the doc numbers as the fallback, so a missing or broken `meters.json` degrades to the documented formula rather than to zero math (`:105-145`).

### Ratchet floor — every write path

| Write path | Where | Does `instability >= floor` hold after it? |
|---|---|---|
| `set_meter` / `adjust_meter` / direct `instability = v` | `GameState.gd:150-164` | yes — `clamped = maxf(capped, instability_floor)`; peak raised to `capped` first, so the floor used is the post-write one |
| direct `instability_peak = v` (new in this patch) | `GameState.gd:113-126` | yes — peak is clamped 0-100, then the meter is lifted to the new floor unless the write came from the meter setter itself (`_peak_guard`, `:205`) |
| `from_dict` restore | `GameState.gd:478-520` | yes — peak is `max(stored_peak, stored_instability)` before any meter write, and the meter loop re-clamps through the setter; `_restoring` (`:206`) keeps the load to one `stage_changed` even when the peak lift crosses a band |
| `reset` | `GameState.gd:215-236` | yes — peak first, then meters |
| `advance_day` (+3) | `GameState.gd:357-363` | yes — goes through `adjust_meter` |
| `apply_mood` / `apply_turn_meters` | `GameState.gd:284-347` | yes — both go through `adjust_meter`; a model delta can only land between the attempt and the floor, never below it |

Lowering the peak does not lower the meter (test at `MetersTest.gd:71-74`), and no production path lowers the peak: the only writes are `reset`, `from_dict` (which raises it to at least the stored meter) and the meter setter. `_peak_guard` is genuinely required, not decoration: without it, the instability setter's peak write would re-enter the peak setter's lift, which would re-enter the setter, ad infinitum.

### Atomic `apply_turn_meters` ordering

`GameState.gd:333-347` does `advance_turn()` → slow burn → mood → ledger snapshot, and `Director.gd:727` is the only production call site (`grep` for `advance_turn`/`apply_slow_burn`/`apply_mood` outside tests/tools finds nothing else). Advancing first is what makes the mood budget correct: `apply_mood` clears `_mood_spent` when `_mood_turn != turn` (`:285-287`), so the turn's mood lands under the new index with a fresh budget, matching the P1.04/P1.29 call order the old Director code documented. The returned ledger is a snapshot after all three steps (`turn`, `slow_burn` landed, mood deltas landed, `instability`, `instability_floor`, `stage`) and `Director.last_meter_ledger` (`:49`) is cleared in `Director.reset()` (`:129`).
