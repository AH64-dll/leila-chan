### CODE-1 — the campaign's day can be an interrupt scenario

`Campaign._pick` (`game/llm/Campaign.gd:105-132`) reduces the pool by availability and by the played set,
then draws one row; nothing looks at the scenario's `kind`. `ScenarioLoader.available_scenarios`
(`game/scenario/ScenarioLoader.gd:164-173`) does not either — it only calls `is_available`, and that
predicate reads `available.days`/`stages`/`paths` (`:145-161`). `ScenarioLoader.pool()` (`:108-133`) lists
every valid `.json` in `res://data/scenarios`, so every kind is in the campaign's pool.

That is harmless in this branch's one-file pool, but main already carries the approved P2.18 content in the
same directory: `D01_classroom`, `D02_cafe`, `D03_park_bench`, `D04_rain_umbrella`, `D06_rooftop`,
`D11_her_room` and `I01_phone_call` (`kind: "interrupt"`, `available` days 1–14 / stages 0–5 / paths `any`).
P2.19 merges on top of that. Driving this branch's own `Campaign.gd` against those seven rows, the day-1
pick at the shipped default seed 0 is `I01_phone_call`; across seeds 0–63, 19 day-1 picks are non-date.
The seed is never assigned anywhere in `game/` (only `Campaign` and `NightLoop` read `campaign_seed`), so
seed 0 is the shipped value and the wrong day-1 pick is deterministic, not occasional.

The design is explicit that a day is a date scene: docs/01 §6.1 calls D01–D18 "Date scenes (main days)"
and §6.2 calls interrupts "random, any day" events that happen *inside* a date. P2.18's handoff also hands
the interrupt injection to P2.19 ("when injecting a `kind: "interrupt"` scenario, keep the parent date's
background/music") — running I01 as the whole day is the opposite of injecting it.

```gdscript
	var rows: Array[Dictionary] = []
	for row: Dictionary in ScenarioLoader.available_scenarios(
		pool, day(), int(_state.stage), String(_state.path)
	):
		var scenario: Variant = row.get("scenario", row)
		if scenario is Dictionary and String((scenario as Dictionary).get("kind", "")) == "date":
			rows.append(row)
	if rows.is_empty():
		return {}
```

### CODE-2 — a night-save Continue loses the played mark

`Campaign.next_scenario` (`game/llm/Campaign.gd:90-98`) sets `FLAG_NEXT_SCENARIO` and returns the row, but
does not append it to `FLAG_PLAYED`; the campaign's class note and the handoff both claim "both picks mark
the scenario played". In the normal loop the morning `Date._apply_campaign_scenario` calls `begin_day`,
which does mark it (`:71-85`), so the invariant holds. It does not hold when the player quits on the night
screen and presses Continue: `SaveSystem.load_latest` puts the night save in `_pending_scene`
(`game/autoload/SaveSystem.gd:128`), the Date consumes it and takes the saved scenario, and
`Date._ready` skips `_apply_campaign_scenario` because `_save_named_scenario` is true
(`game/scenes/Date.gd:184-190`, `:233-252`). My probe (verification 3) shows the result: the day's
scenario is never added to `played_scenarios` and the `next_scenario` flag is still set afterwards.

Impact is visible only once the pool has more than one date (P2.18's six land with the merge): the resumed
day's date can be drawn again while unplayed dates remain, which is exactly what the played set exists to
prevent. The queue flag itself is overwritten by the next night, so it is a bookkeeping leftover.

```gdscript
	var picked := _pick(pool)
	if picked.is_empty():
		return {}
	_note_played(StringName(String(picked.get("id", ""))))
	_state.set_flag(FLAG_NEXT_SCENARIO, String(picked.get("path", "")))
	return picked
```

### CODE-3 — the click-to-skip hint is dead

`Night.tscn`'s root node is a full-rect `Control` with no `mouse_filter` (`game/scenes/Night.tscn:5-12`),
and `Background` is a full-rect `ColorRect` with none either (`:14-21`); both therefore use the default
`MOUSE_FILTER_STOP`. In Godot the viewport delivers a mouse button to the topmost `STOP` control and marks
it handled, so `Night._unhandled_input` (`game/scenes/Night.gd:168-175`) is never reached; the labels are
`IGNORE`, and the containers are `PASS`, so the click dies at `Background`/the root. The skip hint from
`night.json:8` ("click or press Space to skip") is shown after the 3 s window, but clicking does nothing.
I reproduced it on the real scene: after `advance_time(3.5)`, a pushed left-button event leaves
`is_finished() == false`, while a pushed Space finishes the night; setting `mouse_filter = 2` on the root
and `Background` makes the same click finish it (edge and centre of the screen both tested).

This is not caught by `NightSceneTest.test_night_screen_skip_window_comes_from_data` (`:91`) because it
calls `night.skip()` directly instead of pushing an input event through the viewport.

## Summary

The loop is genuinely wired: the day rolls through `GameState.advance_day` (no second burn), the stage
comes from the post-burn meter, the path rule is checked against the post-burn stage and locked by the
crossing, and the event is drawn from the state those steps produced — `NightTest.gd:30`/`:114` prove the
order with data rather than a comment. The two shipped overnights are data, the night screen's clock is
injected and stepped exactly, Esc works on the non-skippable N12, and the autosave/queue round-trip is
tested on the real save slot. All 755 gdUnit cases and 403 pytest cases pass on my run, lint and format
are clean.

Two S2s block the merge. CODE-1 is the campaign's missing `kind` filter: with the already-approved P2.18
pool the default campaign's day 1 is the I01 interrupt — a date day that is not a date, deterministic
because the seed is never assigned. CODE-3 is the night screen's click path: the hint promises a click,
but the full-rect root and `Background` consume the mouse event before `_unhandled_input`, so only the
keyboard works. CODE-2 (the played mark lost on a night-save Continue) and CODE-4 (no test for the
`end_date` action end) are S3s the producer can ticket or fix in the same round.
