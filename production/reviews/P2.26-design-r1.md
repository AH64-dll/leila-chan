## The two questions in the brief

### 1. Is "48 pre-say tokens = 72–76 % of latency" supported by the token census?

**Yes, to within one token and one point of rounding.**

- Census: all 39 recorded turn outputs have a usable `"say":"` landmark; tokenizing each pre-say prefix with the
  server's own tokenizer gives median **49**, min 42, p95 **77**, max 81 (handoff: 34 outputs, median 48). The four
  claimed segments reproduce exactly by tokenizing them separately: `{"read":"…",` **6**, `"inner":"…",` **13**,
  `"music":"…","fx":"…",` **10**, `"beats":[{"feeling":"…","intensity":N,"cue":"…","say":"` **22** (handoff 6/13/10/21.5;
  separate pieces sum to 51 because boundary tokens merge in the concatenation — the handoff says the same).
- Timing agrees with the count: 4362 ms pre-say / 90.3 ms per token = 48.3 tokens over the 39 recorded turns, and the
  replayed artifacts give 4262/88.8 = 48.0 (CPU) and 890/18.55 = 48.0 (CUDA).
- Shares of the first visible character: CPU 4262/5918 = 72.0 %, CUDA 890/1159 = 76.8 %. The handoff's 72.6 %/76.4 %
  comes from (median `first_say` − median `first_token`)/median `visible`; both methods land in 72–77 %.
- The dose-response is the actual causal evidence, and it holds: identical prompts/servers, only schema order changed,
  pre-say tokens 48→30→21→6, pre-say time 890→580→414→148 ms (CUDA) and 4262→2812→1898→568 ms (CPU), per-token cost
  18.5–19.3 ms / 88.8–94.8 ms. Near-proportional, monotone, same per-token slope — that is a measured lever, not a
  correlation.
- The D13 provenance correction checks out independently: `tools/llm/bench_p121.py:70-76,108-118` carries its own
  hand-written "Yui" system prompt and its own schema, so its 7.5 s CPU / ≈1.86 s CUDA numbers cannot describe
  `PromptBuilder`'s prompt. The 39 recorded production turns give 5.36 s first usable `say` (CPU); the handoff's replay of
  session 1 gives 5.229 s and my re-run today gives 6.23 s under the stalls described below. D13's "≈85 pre-say tokens" is the bench prompt's arithmetic
  ((7521 − 391)/88.8 ≈ 80), not the shipped prompt's 48.

Caveats I would put in the record: the CPU-host absolute numbers are not bit-reproducible on this box today — my
re-run decoded at 10.1 tok/s instead of 11.2 and two turns paid 11.1–11.3 s first-byte stalls (cause not
established; the stall lands before the first SSE chunk, so it is not decode time), giving first-say median
6234 ms instead of 5229 ms. The token census (46.5) and the structure
reproduce; the committed `cpu_*` artifacts stay the evidence of record. The CUDA numbers reproduce cleanly.

### 2. Does `music, fx, beats, read, inner` preserve docs/02 §1's timing properties?

**Yes — structurally and by direct measurement, and it preserves the property almost numerically exactly.**

docs/02 §1's stated property is: *music/fx and each beat's feeling/cue arrive before that beat's text, so the face and
sound change exactly when the line starts.* DCR-1 only moves `read`/`inner` behind `beats`; `music`/`fx` stay ahead of
`beats`, and the beat object keeps `feeling, intensity, cue, say` (the harness keeps `BEAT_ORDER_DOCS` for this order,
`tools/llm/latency_breakdown.py`). Every relative assertion in `game/tests/IncrementalJsonTest.gd:262-300`
therefore still holds (see DES-7 on the handoff's claim that the test must change).

I measured the property directly on the RTX 4050 — time the `"music":"…"` value closes minus the time the first `say`
character arrives, four turns per order:

| order | music-close − first-say char (ms), per turn | median |
|---|---|---|
| shipped `read, inner, music, fx, beats` | −518, −482, −463, −462 | **−463** |
| DCR-1 `music, fx, beats, read, inner` | −520, −499, −462, −460 | **−462** |
| `beats` first | +776, +1181, +1185, +1428 | **+1185** |

So DCR-1 keeps the music/fx-before-text relationship to within 1 ms of the shipped pipeline's, while `beats` first
inverts it (music lands 1.2 s *after* the line starts — a real docs/02 §1 violation, correctly rejected). The DCR's
choice of `music, fx, beats` over `beats` first is justified by the same data.

The only fields whose arrival order changes are `read` and `inner`, and neither has a streaming display consumer in
the shipped code: `read` is applied post-turn (`game/autoload/Director.gd:713,729-730` inside
`_apply_turn_repairs_and_deflections`), `inner` is only stored at turn apply (`:714`) and read by the debug overlay
(`game/scenes/debug/DebugOverlay.gd:277`). The docs/03 §5 inner-voice leak — the one design surface that could care —
has no renderer yet. DCR-1's statement that "no display consumer needs them earlier" is therefore accurate today; the
DCR does flag `inner`'s stage-2 leak as the reason quality must be re-measured.

## Summary

The attribution is correct and now has my own evidence behind it: 48–49 pre-say tokens (6 read, 13 inner, 10 music+fx,
22 beat head), 72–77 % of the first-beat latency, with a monotone four-point dose-response and a decomposition that
closes within 22 ms per turn; the DCR-1 order also preserves docs/02 §1 exactly — music lands 462 ms before the first
say versus 463 ms in the shipped order, while `beats` first puts it 1185 ms after. The weak point is not the
order, it is the documentation around it: docs/02 §4's own latency budget is contradicted by the ticket's data and is
missing from DCR-1's doc list (DES-1, S2), and five further items — a prompt-lab schema copy that would let DCR-1's
quality gate pass without testing anything (DES-2), an unreachable cold-prefill benefit in DCR-2 (DES-3), an
under-specified trailing prompt block (DES-4), an inflated 1.6 s figure (DES-5) and an undiagnosed pretty-print tail
(DES-6) — need correcting before the producer decides. Nothing in this review challenges the verdict of the investigation: the shipped path misses the
CUDA target by 16 %, and DCR-1 is the measured fix.
