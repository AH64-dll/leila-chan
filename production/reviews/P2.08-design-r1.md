### DES-1 — "escalates with stage" has no expression in the engine

docs/01 §5 T08: *"Type a message, then delete it unsent · E · 'What were you going to say?' — escalates with stage."* The engine escalates only on the firing count: `_escalation()` is `1 + step_scale × (step − 1)` capped by `max_steps`, and the per-step `line` array is indexed by `step` too (`TriggerEngine._line_for()` `:393-403`). Nothing in the engine reads `ctx["stage"]` for escalation — `stage` is only a pass/fail gate (`_eligible()` `:292-296`). The T08 row this task ships (`behavior: "escalating"`, `step_scale: 0.5`, `cooldown_turns: 2`, no effects, no line) therefore escalates with repetition, not with stage; and because `tests/test_triggers.py:180-185` forbids a `line` on an E row and `data/telemetry.json` carries one stage-static line per event, P2.10 cannot add the stage-dependent reaction to `triggers.json` either.

This is the only trigger in docs/01 §5 whose escalation axis is the stage, so the gap is narrow — but T08 is one of P2.10's fifteen ("All 15 fire in scripted tests with the documented effects"), and the handoff neither implements the axis nor defers it.

Two acceptable fixes; the first is the smaller one and stays data-driven:

```json
"T08": {
  "name": "deleted_draft",
  "detect": { "event": ["draft_deleted"] },
  "behavior": "escalating",
  "escalate": { "axis": "stage", "max_steps": 3, "step_scale": 0.5 },
  "cooldown_turns": 2,
  "stage_min": 1,
  "effects": {}
}
```

with `_escalation()` deriving the step from `ctx["stage"] − rec["stage_min"] + 1` when `axis` is `"stage"`, `step` otherwise (default stays `"step"`, so P3.07's rows are unaffected). Alternatively file a DCR changing docs/01 §5 T08's clause to "escalates with repeats" and leave the row as shipped; either way the decision must be recorded before P2.10 starts.

### DES-2 — the two data-contract decisions need a filed DCR

The handoff's "Deviations" section explains both, and both are defensible:

- `strength.keyword = 1.0` — docs/02 §1.2 only defines "both agree → full" and "model-only → half"; docs/01 §5 has K-only rows that could never reach full strength otherwise. Support.
- `requires: "any"|"all"` — the field that lets a row require agreement. Support.

But neither is in the design text, and the only DCR in the handoff is the docs/07 tree line. P2.10 is instructed by this task's own authoring rules to choose `requires` per trigger and will author T01/T05 (the bible's K+M rows) against it; P3.07 will do the same for T16–T32. One paragraph in docs/02 §1.2 plus the `v1` data-contract note in docs/07 §2 is enough:

> The keyword layer is full strength on its own; the model's `read` alone is half strength; a row may additionally require both (`requires: "all"`), in which case it fires only when every declared detector agrees.

Fix: file it as a DCR (the producer owns the docs/02 and docs/07 edit); no code change.
