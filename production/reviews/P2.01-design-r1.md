## Design interpretations and DCR verdicts

The handoff files no formal DCR. It lists seven readings as "docs are silent". My verdicts:

1. **Formula values live in `game/data/meters.json` with doc-pinning tests — support.** The SYS playbook demands "formulas exactly as written" *and* "everything tunable is data", and it names "a DCR plus data" as the only way to change one. Both suites pin every value to the doc numbers (`MetersTest.test_data_table_matches_docs`, `tests/test_meters.py::test_meters_table_matches_docs`), so a data-only retune fails twice. No doc change is needed.
2. **A peak write lifts Instability to the new floor — support.** docs/01 §2 states the floor as an invariant ("never below `floor = peak − 15`"). A peak raised past the live meter would otherwise leave the documented invariant false until the next meter write, so enforcing it on the peak write is the faithful reading, not a new rule. The lift is a no-op on consistent state (a valid save always has `instability >= peak − 15`), lowering the peak never lowers the meter, and the property sweep exercises raw peak writes.
3. **Stage bands stay in `GameState.STAGE_BANDS`; P2.02 owns "thresholds from data" — support.** docs/01 §3 is not one of P2.01's refs, and P2.02's acceptance criterion is exactly "Thresholds from data". Deferring is correct scoping, not a gap.
4. **`apply_mood()` returns the landed deltas and `advance_day()` returns the landed burn — support.** Additive return values; every existing caller ignores them; docs/02 §4 step 7 constrains the application, not the signature.
5. **`TurnContext.meters()` gains `instability_peak`, `instability_floor`, `slow_burn` — support.** docs/02 §4 step 1 says the context carries "meters"; the additions are state the F3 overlay and the night screen would otherwise recompute. Nothing renders `ctx["meters"]` into the prompt today (only `TurnContext` builds it and tests read it), so the P2.13 system-prompt budget is untouched.
6. **The simulation's player model (Fixation/Lucidity drift, read/mood mix) is scenario input, not a game rule — support.** docs/01 §2 names those drivers qualitatively ("time spent, affection, isolation"; "kindness, honesty, boundaries") with no numbers, and P2.08/P2.12 own the real drivers. Keeping the invented drift in `game/tools/meters_sim.gd` keeps invented balance out of game code.
7. **The `instability_pre` CSV column — support.** It is what lets `tests/test_meters.py::test_curve_burns_match_docs` prove the landed burn is the formula clipped only by the 100 ceiling.

Nothing requires escalation: no pillar change, no safety rule, no docs/09 §4 decision. One un-filed doc edit deserves the producer's attention: `docs/07 §2` was edited in this patch to add `llm/Meters.gd` and `data/meters.json` to the layout. That is factual layout accuracy rather than a rule change (docs/07 §2 is descriptive; the alternative is a stale layout), so I do not treat it as a deviation — but the handoff's "Deviations: None" does not mention it. Suggest naming it in the handoff, and noting that the `GameState.gd` layout bullet ("meters, stage, …") now means "owns the values", not "owns the math".
