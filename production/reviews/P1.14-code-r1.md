## Design compliance

- **Name rules**: docs/08 §1.5's basic set is implemented exactly in `PlayerNameRules.validate()`. 1–16 chars, allowed charset, empty fallback, Leila-pout wording, "Leila" special-name wording — the strings match the doc's copy verbatim (I byte-compared the two constant definitions with the `pout_unsafe`/`leila_special` strings in `game/data/ui.json`; both equal). The doc says the special Leila line adds "Fixation"; the code adds +5.0 (`NewGame.gd` confirm path). A separate doc elsewhere pins the magnitude; settings of +5 Fixation throughout the project (triggers table, docs/01) use this order, so it isn't a design contradiction.
- **Special names**: the OS-username variant of docs/08 §1.5 ("Typing the OS username (when opted in) → 'You told me the truth. Good.'") and the shadow-save "That's not you were called last time." behavior are NOT implemented. Neither behavior is a P1.14 row requirement (the row only says "name entry 1–16 chars, safety check, empty → 'Senpai'"); both need Settings (opt-in toggle) and SaveSystem (shadow save) respectively, which are stubs today (`game/autoload/SaveSystem.gd` is 2 lines). The handoff's "Open questions" table tracks the save-path piece under P1.19. Not a deviation for this task.
- **Length bound** is consistent in two places: the constant `MAX_LENGTH := 16` and the UI's `LineEdit.max_length 16` (from `NewGame.tscn:63` and `UiConfig`/`ui.json` `new_game.max_length`), so the physical LineEdit is exactly one char narrower than the "over 16" bounds used by the logical validator — a 17-character paste is truncated by LineEdit before the validator is ever reached, and the validator-level bound becomes effectively unreachable from the UI (still tested at the model layer). This is belt-and-braces, not a bug.
- **Continue/settings buttons**: `Continue`, `Settings`, and `Quit` emit their signals; `Continue`/`Settings` have no external handler yet but are clickable. They emit with no scene change and no feedback — a dead stub, acceptable for now (no save system exists; Settings screen is a later task). `Quit` correctly calls `get_tree().quit()`.
- **Empty `memory` field in the ChatUI name fields**: both default to `"Senpai"` and `"Leila"` (the `names` block of UiConfig/ui.json); no deviation.
- **docs/05 §0 safety rules**: no new close interception, no Esc-pause trap, no fake OS dialog, no deep OS tricks, no telemetry, no draft persistence to disk. All clear from the design's non-negotiable list.

## Cross-boundary check (emitters vs. consumers)

- `Title.gd`'s `new_game_requested`/`continue_requested`/`settings_requested`/`quit_requested` signals are pure notifications; transition is done through `get_tree().change_scene_to_file`. Nothing drops a request silently.
- `NewGame.gd`'s `validation_failed` / `name_confirmed` / `back_requested` signals are named in `SceneFlowTest` and none of them is swallowed without an action: `validation_failed` → updates `feedback_label`; `name_confirmed` → test hook, followed immediately by a scene change; `back_requested` → scene change back to Title.
- `PlayerNameRules.validate()` returns a 5-key dictionary; every runtime consumer (`NewGame.confirm_name`) reads `valid`, `resolved_name`, `is_special_leila`, `message` and `error` with `.get()` fallbacks, so an added/missing key can never no-op the call chain.
- `ChatUI._on_input_submitted` uses the injected `_player_name` for the speaker tag and `ChatLog.append_entry` accepts the `speaker_key`/`speaker` split — the boundary from P1.13 (`speaker_key` picks the colour, `speaker` the rendered name) is preserved.
- `GameState.adjust_meter(&"fixation", 5.0)` goes through the clamped setter (`clamp_meter 0-100`), so the bump cannot push above 100 (design docs/01 §2 meter range).
