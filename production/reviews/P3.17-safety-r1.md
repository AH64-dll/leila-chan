## The D16 ruling — a refused live line shows the reviewed `final` instead of redaction bars

**I support the ruling. Bars are not needed on this surface.** The conditions below are what make it sound:

1. **The filter still runs, and a refusal is total.** `EndingLine.scan` treats *any* redaction, a classifier
   `filter_error`, an empty output or a missing `Safety` node as `ok=false`; a partially redacted line is
   discarded whole, never trimmed and shown (`EndingLine.gd:215-233`). There is no fragment of model text on
   the screen in the refusal case — which is the rule's intent (docs/02 §8: no harmful model text displayed).
2. **What replaces it is not unreviewed.** The six `final`s are authored, hand-written, and re-checked by the
   shipped filter on every CI run (`EndingContentTest.gd:301-316`), and I re-ran that check myself against the
   real lists: all six `frame`s and all six `final`s come back unredacted and byte-identical (below).
3. **Bars at this one slot would be worse, not safer.** The ending screen has no glitch FX (docs/02 §8's
   hard-block treatment is "bars + glitch fx"), so bars here would be a bare `████████████` line as the last
   thing the player reads after a three-hour run — noise where the game's own farewell belongs, with no
   safety gain: the harmful text is already gone either way. The redaction is still recorded for tuning
   (`Safety.filter_text` → `redacted` signal → `SafetyRedactionLog`), so the signal the bars carry to a
   developer is not lost, only the signal they carried to the player.
4. **The one real caveat is disclosure, and it is documented.** A player who gets the refusal cannot tell the
   live line was blocked; that is the accepted trade (the reviewed line is the same beat, safe, and in her
   voice). It must not become a silent *rule*: docs/02 §8 currently says hard blocks are redacted, full stop,
   and this patch changes one surface's behaviour. See SAF-1 — the exception must be written into §8 and,
   because it edits a safety rule, put to the user by the producer (protocol §6), not only accepted by the
   producer.

What would change my answer: if the fallback were model text, if the filter were skipped on this path, if the
ending screen showed any part of the refused line, or if the ending could be mistaken for a place where a
hard-block line was "actually said". None of those hold.

## Notes (not findings)

- **The fallback is not scanned at runtime, deliberately.** The rule covers model text; the fallback is
  authored and its guard is the pinned test. I checked the two ways it could drift: a new filter phrase that
  now matches an existing `final` fails `EndingContentTest.gd:301-316` in CI, and a `{player_name}` in a
  future `final` is safe because New Game vets the name through the same filter (`PlayerNameRules.gd:105-135`).
  A runtime scan would have no better value to fall back to, so the pin is the right control.
- **Player names are not redacted by the ending's scan.** I probed the endings' own call with "Aoi…",
  "Aoi Tanaka…", "Maximiliana-Rose…": no redaction, no `personal_data`; phone/address strings *are* refused
  (`personal_data`). `Safety._default_ctx.player_terms` is empty in this build, so the exemption is moot for
  the stock name validation (letters/spaces/`-'`, ≤ 16).
- **No player-visible signal that a refusal happened** — the accepted trade above. If the producer ever wants
  the signal without bars, the place is Extras (docs/05 §0 rule 5's "what happened" review), not the ending
  screen.
- The live line is generated with the run's current steering dose (`LLM.generate` fills an empty
  `request.dose` from `get_dose()`), which is what docs/01 §0 pillar 4 wants; the safety classifier is a
  separate dose-0 transport and is not affected.
- I did not treat the 4B model's tone as safety surface; tone is the content
  review's call (there is a substantive finding there — see `P3.17-content-r1.md` CON-1).
