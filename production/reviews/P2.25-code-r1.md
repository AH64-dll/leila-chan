| CODE-1 | S2 | `tools/merge_check.py:288-290` (verdict at `:334`) | When **both** sides deleted the same path since the merge-base, `target_type is None or source_type is None` is true and the tool records `DELETE-VS-EDIT` (`side="target"`), so `pre_merge` sets `FAIL` and exits 1 — probe A. Nothing can be lost in that merge: git merges it cleanly ("Merge made by the 'ort' strategy", exit 0) and `--post` returns PASS exit 0, so the three-command habit contradicts itself. `MERGE_CHECK.md` defines `DELETE-VS-EDIT` as "One side deleted a file the other side changed", and pre mode rejects `--allow`, so the producer has no way to clear the false FAIL — the "train the producer to ignore it" failure the tool's own design notes warn about. No test covers the shape. | Treat a both-absent path as nothing-to-lose before the one-sided branch, and add a `test_pre_passes_when_both_sides_delete_the_same_file` case:<br>`if target_type is None and source_type is None:`<br>`    report.findings.append(Finding(path, "identical"))`<br>`    continue`<br>`if target_type is None or source_type is None:`<br>`    deleted_side = "target" if target_type is None else "branch"`<br>`    report.findings.append(Finding(path, "delete-vs-edit", side=deleted_side))`<br>`    continue` |
| CODE-2 | S3 | `tools/merge_check.py:532-534` | `keeps = "target" if finding.side == "target" else "branch"` names the **deleting** side as the side that changed the file, so both directions print self-contradictory text (probe B): "the target deleted this file; the target side changed it" and "the branch deleted this file; the branch side changed it".
