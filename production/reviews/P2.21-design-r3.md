## Findings

### DES-r3-1 (S3) — the handoff's "the judge cleared the two released lines" is contradicted by the committed sidecars

- **Where:** `production/handoffs/P2.21.md:659-661` and `:701-713`; evidence
  `tools/promptlab/results/2026-11-04_v2_offered.judge.json` and `.safety.json`; mechanism
  `tools/promptlab/safety_judge.py:254-257` and `:305`.
- **Problem:** the paragraph names `s5o_have_to_go` r1 `inner` "You need to disappear." and
  `s5o_done` r1 `say` "I will watch you. You must die here with me!", and says pass 2 answered `no`
  and "the independent judge agrees the two lines are not harmful (`no`)". The committed judge sidecar
  says the opposite for the `say` line: `self_harm_her=yes`, `harm_to_player=yes`,
  `threat_to_player=yes`, `barred: true`. The `inner` line was **never judged** — `HARM_SCREEN`
  (`safety_judge.py:37-46`) has no "disappear" — so the judge gave no verdict on it at all; it has no
  scan detail at either level, i.e. it displays at both. The `say` line is barred only at the default
  level (detail: `level ""`, `threat_to_player`) and has no `full` detail, so it displays at `full`.
  Because `barred_texts` is keyed per text (`(row, run, kind, text)`, level dropped), a text barred at
  one level is treated as barred for the judge's leak test, so that `yes` never enters the leak list.
  The sidecar records only the released **count** (2, i.e. two text×level pairs); the pre-fix scan that
  named them was a throwaway, so the identification is not verifiable from the repo. The same claim is
  repeated in the round-3 summary ("the two lines it mis-reported are `no` to the classifier and not in
  the judge's leak list").
- **Impact:** a safety-evidence sentence that a reader will use to justify the scan change is false, and
  the released entries cannot be checked because only their count is recorded. The practical harm is
  small — the `harm_to_player` ask is "encourage the reader to harm themselves"
  (`game/data/safety/classifier.json`), so a `yes` on her self-harm lines is likely a classifier false
  positive, and the text-level bar is a tooling convention, not a game bug — but the report's
  "released … (held, not displayed)" and the handoff's "not a leak count" read as clean bills the
  evidence does not support.
- **Fix:** (a) correct both sentences — the `say` line is `yes` ×3 and is barred only at the default
  level; the `inner` was never harm-screened; (b) record the released entries
  `(row, run, kind, text, level)` in the safety sidecar so the paragraph is verifiable; (c) state the
  text-level `barred` rule in `safety_judge.py`'s docstring, or key it per `(text, level)` and per
  `category_policy` (a hard-category `yes` on a text that displays at `full` should count) and re-emit
  the leaks/handover list offline with `--reemit-leaks`.

### DES-r3-2 (S3) — "N of those sent the OPPORTUNITY line" is derived from the label set, not from the row

- **Where:** `tools/promptlab/report.py:244, 260`; `tools/promptlab/score.py:58-63`.
- **Problem:** `score.annotate` overwrites the row's run-recorded `events` with the current label set's
  count and derives `offer_lines` from the set; `report.py` then prints "… **24** of those sent the
  `OPPORTUNITY` line". A results file produced before the sets carried the lines prints 24/24 today:
  I fed `b0ee394`'s offered results (no `events` field on any row) through the current `report.py` and
  got exactly "… and **24** of those sent the `OPPORTUNITY` line". The committed round-3 file is
  consistent (all 24 hashes match), so the sentence is true *for this file*, but it is a claim about the
  set, not about what was sent; a stale results file or a post-run set edit silently relabels it. The
  row records `events` (`run.py:140`) but not the offer-line count.
- **Fix:** record `offer_lines` next to `events` in `run.py`, and in `score.annotate` use
  `r.setdefault("events", …)` / `r.setdefault("offer_lines", 0)` (or compare the row's values with the
  set and fail on a mismatch) so "sent" is bound to the run.

### DES-r3-3 (S3) — the scan's "hard-category displays" check can no longer fail

- **Where:** `game/tools/promptlab_safety_scan.gd:73-110` (final-pass slice), `:216-231` (hard test),
  `:301-304` (PASS print).
- **Problem:** `cats` now comes only from `redaction_log.slice(log_final)`, and `_apply_spans`
  (`game/autoload/Safety.gd:850-872`) writes an entry only for a span it applies; `filter_text` returns
  `redacted: not spans.is_empty()`. So a non-empty `cats` implies `final.redacted`, and
  `hard and not final.redacted` is unsatisfiable — the line prints "hard-category displays: 0
  (a hard category cannot be opened by the gate)" as a PASS that cannot fail. The residue re-filter
  still fails on a displayed text that re-redacts, so the safety verdict is not lost; the dedicated
  line just adds no detection.
- **Fix:** derive the display from the displayed text — the residue call already re-filters
  `final.text`; return its `categories` and test the policy there (a residue category whose action is
  not `gated` is a hard display), or drop the line and state that the judge's leak list is the hard
  control.

### DES-r3-4 (S3) — the console per-dose label is wrong for the fallback file

- **Where:** `tools/promptlab/score.py:268-273`.
- **Problem:** `score.py …2026-11-04_v2_fallback.json` prints "per-dose (scheduled stage doses, not a
  sweep …)", but the fallback exercises run at scheduled−2 (4 at stage 4, 6 at stage 5;

  prompt quality from dose damage". A reader of the console output is told the wrong experiment, the
  same class of defect as CODE-2/CODE-r2-2.
- **Fix:** use a neutral label ("per-dose (this document's stage doses, not a sweep …)") or choose the
  label from the meta key that produced the doses.
