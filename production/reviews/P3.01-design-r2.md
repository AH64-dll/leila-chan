## Later-phase dependencies (P3.03 / P3.04)

- **Open item — Windows pass.** The amended criterion still carries one verification on the design machine. It must be recorded wherever the producer tracks follow-ups (`STATUS`/`DECISIONS`) before P3.01 is closed; otherwise the plan row's own wording is unmet even though the code is done. Not a P3.01 code defect.
- **Volume.** Each prompt dump is ~11.3 MB (11 × ~100 × 2560 × 4). 200 pairs × 2 sides × 6 vectors is ~27 GB; the volume has 139 GB free, so it is workable but should be planned (one vector at a time, or a token-subset/last-token option).
- **Pair shape.** The tool renders one single-turn user message per line. If NAR's contrastive pairs are two *assistant replies* to a shared prompt, the tool needs multi-turn rendering; if they are two user prompts, the current format is sufficient. The `.npy` keeps all tokens, so any token slice is a numpy op.
- **Persona.** The sanity dumps use the §1 placeholder Yui persona; the shipping prompt is `game/data/prompts/persona.md` (Leila). Decide for P3.03 whether extraction should run under the shipping persona — the design is silent.
- **Checker assumption.** `check_malice.py` normalizes the direction tensors while the runtime adds them raw. With the committed unit vectors (norm 1.0) the `shift == scale` expectation is exact; a non-unit vector would make the checker's expected shift wrong (it could only false-fail, not false-pass). Worth a comment in the script.
- **Exit codes.** The new contract (0 ok / 1 runtime-or-skipped / 2 bad input) is what a 200-pair P3.03 run should branch on; the one gap is a missing argument value exiting 1 (code review CODE-11).
- **Regenerability.** The dumps are gitignored (~204 MB); a fresh clone must re-run. Re-proved this round: a from-scratch build reproduces all 20 files byte-identically.
