# Spike P0.09 — NobodyWho vs own GDExtension (feeds P4.01)

**Date:** 2026-11-02 · **Agent:** LLM (swe2) · **Task:** evaluate the NobodyWho Godot plugin
against our four runtime requirements and feed a recommendation to P4.01 (runtime decision) /
P4.02 (GDExtension build).

**Candidate evaluated:** NobodyWho for Godot **v13.0.0** (released 2026-10-29), the prebuilt
GDExtension from `nobodywho-godot-v13.0.0.zip` (362 MB, 1.2 GB unpacked — one fat binary per
platform bundling llama.cpp + ONNX-Runtime speech stack). Rust core over a nobodywho fork of
`llama-cpp-rs`; licence **EUPL-1.2**. Requires Godot ≥ 4.6 — our pin is 4.7.2, OK.

**Design rule being tested** (docs/07 §1): *"if it exposes control vectors + JSON schema, use it;
otherwise our extension is a thin (~800 lines) wrapper."*

## Tested minimal example

The minimal project's sources are committed at `docs/spikes/p0.09_nobodywho_test/`
(`project.godot`, `main.tscn`, `main.gd`). The whole backend is ~10 lines:
`NobodyWhoSamplerBuilder.new().json_schema(schema).penalties(...).temperature(0.8).dist()`,
`NobodyWhoChat.create(model_path, cfg)`, `chat.complete(msgs)` → `stream.next_token()`.

```bash
# reproduce (this machine: Godot 4.7.2 in tools/godot, model at D:/lila/models)
# 1) copy docs/spikes/p0.09_nobodywho_test/ to a scratch dir OUTSIDE the repo
#    (Godot writes .godot/ inside the project — never run it in-tree)
# 2) download nobodywho-godot-v13.0.0.zip from github.com/nobodywho-ooo/nobodywho/releases
#    and place into <scratch>/addons/nobodywho/: nobodywho.gdextension, LICENSE,
#    libnobodywho-godot-x86_64-pc-windows-msvc-release.dll   (143 MB — do not commit)
# 3) headless:
GODOT="/d/lila/tools/godot/Godot_v4.7.2-stable_win64_console.exe"
"$GODOT" --headless --path <scratch> --import   # once: registers the .gdextension
```

## Verdict — for P4.01

**Build our own GDExtension (`libleila_llm`), keep llama-server for the prototype/prompt-lab.**
This matches the design's own decision rule: NobodyWho has the JSON-schema half but not the
control-vector half, and control vectors are the load-bearing feature — the dose schedule,
path-vector mixing and trigger spikes (docs/06 §3/§4) all need `llama_set_adapter_cvec` called
per turn on one long-lived context.

Secondary factors, same direction:

- Vulkan-only Windows GPU showed 8–25× run-to-run variance and ~1.75× the server's VRAM on our
  exact target GPU; docs/07 §6 already plans CUDA **and** Vulkan per platform — we'd ship CUDA
  ourselves regardless.
- EUPL-1.2 copyleft on a commercial Steam release needs legal review; a fork carrying a cvec
  patch inherits EUPL and removes the licence escape hatch.
- 143 MB bundled runtime carries STT/TTS/ONNX we never use; a thin wrapper is ~800 lines and
  keeps llama.cpp pinned/upgradeable.

What NobodyWho *would* be good for here: a drop-in **prototype/prompt-lab** backend if
llama-server ever became painful — the grammar/streaming/template-variable surface proved it
can drive a full Turn end-to-end. It is also a working reference implementation of
Godot↔llama.cpp async plumbing worth cribbing for P4.02.
